- **Split `ItemSeries` into `TaskSeries` and `EventSeries` at the domain level**, the same way `Item` was split into `TaskItem`/`EventItem`/`TemplateItem`/`SimpleItem` (`docs/archived/item-kind-split-plan.md`, and root CLAUDE.md's Domain Models section). Raised 2026-09-05, on exactly the same grounds as that split: one type serving two cases means every field only some series can legitimately carry is an `Option` (or a silently-meaningless value) policed by a runtime check instead of being unrepresentable. The current offenders on `ItemSeries` are `cursor_date` (Task-only — an Event series has no completion concept and never advances it, always `None`), `basis` (`COMPLETION`/`DUE_DATE` both Task-only, rejected for Events by `validate_series_basis`), `assigned_to_user_id`/`points` (Task-only *and* team-backed-project-only, via `resolve_series_assignment`), `priority` (Task-only, via `validate_series_priority`), `event_type` (unsupported on *any* series today — see `validate_series_event_type` — so it's a field no variant would carry), and the new sub-item definitions (`item_series_children`, Task-only, since an Event item can't have children at all). Each of those is a `validate_*` call that a variant-carrying enum would make unnecessary. Follow the item-kind-split plan's own staging discipline: one field at a time, not a big-bang rewrite.
  - **Prerequisite, now done (2026-09-05): a series' `item_type` is immutable.** It used to be a plain full-replace field on `UpdateItemSeries`, so editing a series could flip Task↔Event — which left every already-materialized occurrence at the old kind while future ones materialized at the new one, and orphaned whatever kind-specific state the old kind carried. `service::item_series::update_series` now rejects a mismatch outright (`update_series_rejects_changing_the_item_type`), and the web edit dialog renders Kind read-only.
  - **Still to do on the immutability side, before the split:** `itemType` is still a required member of the `UpdateItemSeries` Smithy input, so every caller has to send the value it already has just to have it checked — `todo-cli`'s `prl series update --item-type` (currently a hard-required flag), the MCP `update_item_series` tool, `src/json_api/item_series.rs`, and the web edit form's hidden input all round-trip it for no reason. Removing it from the Smithy input (plus `task codegen`) drops all four at once and makes the guard in `update_series` dead code that can go with it — at which point the kind genuinely can't be expressed on an update, rather than being expressible and rejected.
- **Remove scheduled-date basis for Task series entirely — due date becomes the only recurrence basis for tasks; Events keep scheduled.** Decided 2026-09-05. Rationale: a series' recurrence rule is defining a *due date*. Scheduling is a per-instance construct — the particular circumstances of one occurrence bear on when exactly you plan to do it — so it has no business being what a recurrence rule produces. The UI half is folded into the series sub-items work and **landed with its Stage 4 (2026-09-05)**: the blank "Schedule" `<option>` is gone from both series forms, Due date is the default, and an existing scheduled-basis Task series matches no option — it lands on Due date and converts on its next save, with an inline amber note on the edit form saying so. **This entry is the backend half, still to do:** retire `is_due_date_basis` and the two-branch materialization in `service::item_series::get_or_materialize_occurrence`, which currently writes `scheduled_date`/`has_scheduled_time` for a Task series unless `basis == "DUE_DATE"`; make `validate_series_basis` reject anything but `COMPLETION` on a Task series (`basis` is doing double duty — `COMPLETION` is the orthogonal settle-from-actual-completion-time flag and stays); decide what happens to existing rows (a migration setting Task series to due-date basis, versus leaving legacy rows reading scheduled — the former, most likely, since the point is that there is only one basis); then drop the now-dead branch from `ProjectOccurrence::is_due_date_basis` and every template that reads it. Closing this also closes the sub-items gap below, which exists only because a Task occurrence can currently land on `scheduled_date`. (The related `copy_template_children` anchor entry that used to sit above this one is already archived — Stage 3 of the sub-items work deleted that call site outright.)
  - **Blocked on this: a materialized series sub-item on a scheduled-basis series lands with no due date at all** (found 2026-09-05 while implementing Stage 2 of the sub-items plan). `create_item` recomputes `due_date` for anything with a `parent_item_id`, from `item_anchor` of its top-level ancestor — and `item_anchor` reads `due_date` only, never `scheduled_date`. A scheduled-basis occurrence has no `due_date`, so its children's dates get cleared. Not introduced by the sub-items work: `create_project_task_series_occurrence_child_form` already does the same thing, so every hand-added sub-item on such an occurrence is already undated today. Visibility *before* materialization is unaffected (`fan_out_child_occurrences` computes lead-time dates from the definition and the cycle date, with no item involved); the damage is that a materialized sub-item sorts last and drops off both calendars. Pinned by an explicit `item.due_date().is_none()` assertion in `materializing_a_sub_item_materializes_its_parent_and_nests_under_it` so that changing it is deliberate and has a failing test attached.
- **An item created in a user's *second* team-less project is filed under the wrong project and the request then fails.** Found 2026-09-07 while doing Stage 8 of `docs/archived/typed-item-params-plan.md` (which surfaced it but did not cause it — the behavior is unchanged since the Project abstraction's stage B2 dual-write). `service::project_items::create_project_item` dispatches a project with no backing team to `items::create_item`, which sets the new row's `project_id` from `ProjectRepo::find_personal_project(user_id)` — `WHERE owner_user_id = ? AND team_id IS NULL LIMIT 1`, i.e. an arbitrary one of the user's team-less projects — rather than from the `project_id` the request actually named. `service::projects::create_project` always passes `team_id: None`, so owning several team-less projects is ordinary, not an edge case. The row lands under the first one; `create_project_item`'s own post-create `repo.get_by_project(&project_id, &item_id)` then can't find it and the request returns NotFound, leaving a misfiled row behind. The team-backed branch is unaffected (`create_team_item` uses `new.project_id` directly), and so is update (`items::update_item` carries `project_id` forward from the stored item). The fix is presumably to pass the requested project down instead of re-deriving it, but that touches the dual-write's whole reason for existing (keeping the legacy `user_id`-keyed read APIs consistent — see `items::create_item`'s doc comment), so it wants its own look rather than a drive-by change.
- **Id-shape question for virtual-row composite ids, raised 2026-09-06, not decided.** The sub-item row id is `child:{child_id}:{ts}` (a literal prefix as discriminator, since `{child_id}:{ts}` is shape-identical to an occurrence's `{series_id}:{ts}`), whereas the URL for the same thing uses the three-part `{series_id}/{ts}/{child_id}`. A uniform three-part id (`{series_id}:{ts}:{child_id}`) would discriminate by arity instead of by magic prefix and match the URL, at the cost of carrying a `series_id` the `child_id` already resolves. Worth folding into whatever touches `parse_virtual_row_id` (`src/web_ui/project_tasks/handlers.rs`) next rather than changing on its own.
- **`service::item_series::max_child_lead_days` should be a single `MAX(days_before)` repo query.** Added by Stage 5 of the series sub-items work so the calendars can widen their occurrence query far enough to catch lead-time sub-items whose parent cycle falls outside the visible range (a sub-item shown on the 1st can belong to an occurrence 30 days later). As written it loops every Task series in the project and calls `list_series_children` per series — one query per series per calendar load, on both `project_calendar.rs` and `main_calendar.rs` (the latter per project) — and then `fan_out_child_occurrences` immediately re-reads the same definition rows. One `SELECT MAX(days_before) FROM item_series_children` scoped to the project's series would collapse the first half; passing the already-read definitions through would collapse the second. Noted at the function too, but tracked here so it isn't buried.
- **Confirm that deleting a materialized series sub-item makes it reappear as a virtual row, and that this reads as intended.** By design (sub-items plan, third consequence): delete un-materializes rather than excludes, mirroring `delete_occurrence` vs `mark_exdate` at the parent level, and since the definition still exists the row is recomputed on the next render and still blocks the parent's completion. The way to be rid of a sub-item is to delete its *definition* on the series, or — once it exists — to set the planned per-sub-item "non-blocking" flag. - **In-place row expansion collapses whenever a list re-renders.** `toggleChildren` (`templates/base.html`) is pure DOM state — nothing persists which parent rows were expanded — so any action that rebuilds `#items-list` or re-fetches `#page` closes every open subtree. Pre-existing (a virtual occurrence's "Mark complete" has always rebuilt the whole list), but it got more noticeable on 2026-09-06 when a virtual sub-item's edit-save and a materialized occurrence's Reset both started re-rendering in place: both act on a *nested* row, so the row the user just changed ends up hidden behind a collapsed parent. Neither action can avoid the rebuild — materializing a sub-item changes its row id and can materialize its parent alongside it, and a reset replaces a real row with a recomputed virtual one — so the fix belongs in expansion state, not in those actions: remember the expanded set per screen (`localStorage`, the way `sidebar-collapsed` already works) and re-apply it after a swap.

- Should events have "save as template" ability? Not sure we need event templates, but perhaps — maybe templates should be called task templates to clarify the narrower purpose if we decide to rule out event templates. Needs a decision from the user, not sized as a task.
- Remove the `dueDate`/`dueTime` field from Events (new-event form, event detail/edit views, series-occurrence views). Currently allowed by both backend (`Item::validate()` has no rule against `due_date` on `ItemType::Event` — `Schedule`, the struct holding `due_date`/`scheduled_date`/`scheduled_end_date`, is shared by `Task` and `Event` alike) and UI (deliberately exposed, labeled "separate from the scheduled window above"). Conflicts with the widely held concept of a calendar event, which has a scheduled time/window but no separate "due" date.
