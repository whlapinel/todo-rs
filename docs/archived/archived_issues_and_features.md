- ~~Dockerfile: I think combining these commands is defeating the purpose of the first command "dummy main". The build takes forever EVERY time:~~ Fixed, but the real cause wasn't the combined `&&` commands — it was that `task docker-build` runs `task codegen` before every `docker build` (`Taskfile.yml`), which regenerates the gitignored `todo-server-sdk/` from scratch each time. That directory's `COPY todo-server-sdk/ ./todo-server-sdk/` layer isn't byte-for-byte reproducible run to run (Gradle-based codegen), so it cache-missed on nearly every build — which invalidated every layer after it in Docker's ordinary layer cache, including the expensive "dummy main" dependency-compilation step, regardless of whether `Cargo.lock` had actually changed. The dummy-main trick was doing exactly what it was supposed to; Docker's layer cache was just the wrong tool for a workflow that regenerates an upstream `COPY`'d directory on every build. Replaced it with BuildKit `RUN --mount=type=cache,...` mounts for `/usr/local/cargo/registry` and the `target/` dir (`Dockerfile`'s `rust-builder` stage) — these persist across builds independent of Docker's layer cache, so cargo only actually recompiles what changed. Since a cache mount's contents don't land in the final image, the built binary is `cp`'d out to a normal path before the mount unmounts, and stage 3's `COPY --from=rust-builder` now pulls from that path instead of `target/.../release/todo` directly. Verified live: built the image once (~3 min, cold cache), then touched a file inside `todo-server-sdk/` to simulate what a fresh `task codegen` run does before every `docker build`, and rebuilt — the SDK `COPY` layer cache-missed as expected, but the second build finished in 41 seconds since the cargo registry/target caches were untouched by that invalidation.
