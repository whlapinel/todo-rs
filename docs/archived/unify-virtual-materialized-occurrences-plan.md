# Unify virtual & materialized series occurrences

Status: **Stages A, B, C, and D implemented (2026-08-19). Complete.**

## Context

This is `docs/archived/archived_issues_and_features.md`'s last open item (labeled "Major change" there) and `docs/archived/archived_issues_and_features.md`'s ranked item 2, treated as one piece of work rather than two, since they're the same request from two angles:

> "I want virtual occurrences to look the same as materialized occurrences, except that I want to carry over the UI from virtual rows (e.g. display current if current, and skip action is available). This implies that skipping should be available for materialized occurrences, which means we need to essentially delete the occurrence and skip it in a single pass for that path. Additionally and more broadly, I want to materialize only when necessary, i.e. when marked complete, or when the occurrence is actually modified in some other way. So we need to have a way of viewing details for a virtual occurrence that looks the same as materialized occurrences - just use the series id and occurrence date instead of the item id for the URL. I want the distinction between virtual and materialized to be fully hidden from the user."

`issues.md`'s ranked item 2 already independently arrived at the same "skip a materialized occurrence = delete + exdate in one pass" conclusion, plus three still-open gaps: (a) no link from a materialized item's detail page back to its series, (b) no visible "skipped" indicator anywhere, (c) no "unskip" action.

### Key findings from research (three parallel investigations, 2026-08-19)

- **`items` had no `series_id` column.** The only link from a materialized item back to its series was a reverse lookup, `ItemSeriesRepo::find_occurrence_by_item_id`, used only by internal write-path hooks (complete/uncomplete/delete gates in `service::project_items::update_project_item`/`delete_project_item`) — never by any render path. The user asked for this column twice in `issues.md`'s history. **Added in Stage A** — see below.
- **The URL-hiding ask is looser than it first sounds.** The user's own wording — "hidden from the user... unless they are observant enough to deduce from URL differences" — means materialized items can keep their existing URLs (`/tasks/:id`, `/events/:id`) unchanged; only a *new* route for still-virtual occurrences is needed (keyed by `series_id`+`occurrence_date`), plus making the two look the same wherever they're rendered. This significantly shrinks Stage C/D's scope versus migrating every existing item URL onto a series-scoped scheme.
- **"Materialize only when necessary" reopens a decision made the other way on purpose.** Stage 5 of the original item_series design (`docs/archived/recurring-events-virtual-occurrences-rough-plan.md`) explicitly considered lazy materialization and rejected it: "the user confirmed materializing on click/view is fine." Not a blocker — the same user is revisiting it — but Stage C should be built knowing it's a deliberate reversal, not a gap-fill.
- **"Skip on a materialized occurrence" is already precisely specified**, and composes two existing primitives: `unlink_deleted_item_occurrence` (already un-materializes on plain delete, without marking exdate — this was itself a three-pass design correction recorded in `issues.md`, concluding that delete and skip are different intents) and `skip_occurrence`'s `mark_exdate` + cursor-advance. Stage B just needs a thin wrapper that does "if materialized, delete the item first" before doing what `skip_occurrence` already does.
- **`docs/scheduled-catchup-plan.md` is a landmine, not part of this work.** It's written against the old item-level `recurrence` field (retired in Stage 10 of the item_series redesign) and has zero series-awareness. If implemented as currently written, its "reschedule overdue items" bulk action would directly overwrite `scheduled_date` on a stale materialized series occurrence — desyncing it from the series cursor and reintroducing the exact "stuck series" bug fixed 2026-08-19 (see `issues.md`'s "major bug" entry). **Whoever picks up `scheduled-catchup-plan.md` next must add a `series_id IS NULL` guard to its query** — trivial now that the column exists, but easy to miss if that doc is implemented blind. Not otherwise touched by this plan.

## Staging

Four stages, each a separate, independently committable/reviewable unit. Per the user: commit at the end of each stage, then clear context before starting the next one — each stage below is written to stand alone for a fresh session.

### Stage A — foundation (implemented 2026-08-19)

Purely additive. Nothing in `web_ui` changed; no existing behavior changed.

- `items.series_id TEXT` (nullable), migration `AddItemSeriesId` (version 23), index `idx_items_series_id`. Added to baseline `CREATE TABLE IF NOT EXISTS items` too.
- `Item.series_id: Option<String>` (domain). Not user-settable — no Smithy field, CLI flag, or MCP parameter. Set once, only by `service::item_series::get_or_materialize_occurrence`, via a new internal-only `series_id` field on `CreateItemParams`/`CreateTeamItemParams`/`CreateProjectItemParams`. Every JSON API/web UI/import construction site explicitly passes `None`.
- Carried forward on every update (`items::update_item`, `team_items::update_team_item`) from `current.series_id`, the same way `project_id` already is — an item's series membership never changes after creation.
- New service function `item_series::list_occurrence_states_for_project` + `OccurrenceState { Materialized { item_id }, Skipped, Virtual }` + `ProjectOccurrence`, alongside the existing `list_virtual_occurrences_for_project_unchecked`. Where that function *excludes* any date with an `item_occurrences` row, this one classifies every candidate date into one of the three states — the single data source Stage D's rendering unification builds on, so screens stop separately querying materialized items and virtual occurrences and merging them by hand. Returns `item_id` only (not a full `Item`) for materialized dates, so callers batch-fetch via their existing `list_by_project`/`list_due_by_project` calls rather than duplicating item-fetch logic. **New and unused by any `web_ui` code as of Stage A** — Stage D wires screens onto it.

Critical files: `src/storage/migrations/add_item_series_id.rs`, `src/storage/sqlite/mod.rs` (baseline table/index, `row_to_item`), `src/storage/sqlite/items.rs` (SELECT/INSERT/UPDATE), `src/domain/item.rs`, `src/service/items.rs`, `src/service/team_items.rs`, `src/service/project_items.rs`, `src/service/item_series.rs`.

### Stage B — skip/unskip unification + series link (implemented 2026-08-19)

- `item_series::skip_or_delete_series_occurrence` (`src/service/item_series.rs`): given `(series_id, occurrence_date)`, if the occurrence is materialized (`ItemSeriesRepo::get_occurrence` returns an `item_id`), first deletes the item via the existing `project_items::delete_project_item` (which already calls `unlink_deleted_item_occurrence`, reverting the row to virtual/no-row), then runs the existing `skip_occurrence` logic (`require_current_occurrence` gate, `mark_exdate`, cursor advance) unchanged. A *composition* of two already-correct primitives, not new mutation logic, as planned.
- `item_series::unskip_occurrence`: mirrors `record_task_uncompletion`'s cursor-safety rigor exactly. For a Task-typed series, rejects unless `occurrence_date == series.cursor_date` (no self-heal past it, same asymmetry `require_cursor_occurrence` already has for uncompleting), then retreats the cursor one step (`recurrence::retreat_once`) or clears it via `clear_cursor` if `occurrence_date == series.anchor_date`. For an Event-typed series (no cursor), any exdate occurrence unskips unconditionally. Both branches finish with `ItemSeriesRepo::delete_occurrence` to remove the exdate row. Rejects outright (before touching the cursor) if the occurrence isn't actually marked exdate.
- New route `POST /projects/:project_id/series/:series_id/occurrences/:occurrence_ts/unskip` (`unskip_project_item_series_occurrence_form`), alongside the existing `.../skip` route, which now calls `skip_or_delete_series_occurrence` instead of `skip_occurrence` directly — the one Skip button works whether the occurrence it's attached to is virtual or materialized, no new endpoint needed for that half.
- **Redirect-based UI, not in-place fragment swap.** The Skip/Unskip route is shared by five different screens (Tasks list/calendar, Dashboard list/calendar, Events calendar), and unlike the old "skip empties the response, row disappears via `hx-swap=outerHTML`" behavior, a skipped occurrence now needs to *stay visible* (struck through, with an Unskip button) — which means the response has to render correctly for whichever of the five screens made the request. Rather than teaching the generic series-scoped handler how to render five different fragment shapes, both handlers redirect back to `HX-Current-URL` (the URL htmx sends automatically on every request) via the existing `hx_redirect` helper, so the origin screen just re-renders itself with the mutation already applied. This trades the old snappy in-place removal for a full-page reload, matching the same tradeoff `create`/`update`/`duplicate` series already make.
- Visible "skipped" indicator: every occurrence-rendering call site (`project_tasks::{mod.rs's render_rows_with_virtual/build_calendar_days, handlers.rs}`, `project_dashboard.rs`'s list/calendar, `project_events::{mod.rs's build_calendar_days, handlers.rs}`) switched from Stage A's `list_virtual_occurrences_for_project_unchecked` (which silently dropped any already-settled date) to `list_occurrence_states_for_project`, filtering out only `OccurrenceState::Materialized` (already rendered via the real item query) and keeping `Virtual`/`Skipped`. `list_virtual_occurrences_for_project_unchecked` and its `VirtualOccurrence` struct had no remaining callers after this switch and were deleted rather than left as dead code. Each screen's row/calendar-entry struct gained `is_skipped`/`unskip_url` fields; each template conditionally renders a struck-through name + "Skipped" label + Unskip button in place of the materialize link/Skip button. The Tasks flat list (which only ever shows the series' single *current* occurrence) needed no template change beyond the type swap — by construction (`require_current_occurrence`'s self-heal) the current occurrence is never itself materialized or skipped, so the indicator only actually shows up on the calendar/dashboard views that render a real date range.
- Series link on a materialized item's detail page: `item.series_id.is_some()` → fetch the series (`ItemSeriesRepo::get_series`) → render a "Part of series: {name}" link to the series' edit page (`/web/projects/:project_id/series/:series_id/edit` — there's no dedicated series *detail* page, only list/edit). Implemented for both Tasks (`ProjectTaskDetailView::series_link`, `resolve_series_link` in `project_tasks/templates.rs`) and Events (`ProjectEventDetailView::series_link`, `resolve_series_link` in `project_events/templates.rs`). Closes `issues.md` ranked item 2(a).

Critical files: `src/service/item_series.rs`, `src/web_ui/project_item_series/handlers.rs`, `src/main.rs`, `src/web_ui/project_tasks/{mod.rs,handlers.rs,templates.rs}`, `src/web_ui/project_dashboard.rs`, `src/web_ui/project_events/{mod.rs,handlers.rs,templates.rs}`, `templates/project_tasks/{virtual_row.html,calendar_page.html,detail_view.html}`, `templates/project_dashboard/{virtual_row.html,calendar_page.html}`, `templates/project_events/{calendar_page.html,detail_view.html}`.

### Stage C — deferred materialization + virtual occurrence detail page (implemented 2026-08-19)

- New `GET /projects/:project_id/series/:series_id/occurrences/:occurrence_ts` route (`project_item_series::handlers::project_item_series_occurrence_detail_page`), sharing its path with the existing POST materialize route: **no side effect** — never calls `get_or_materialize_occurrence`. If the occurrence is already materialized, redirects (plain 3xx, htmx-boost-transparent) to the item's real, permanent URL (`project_dashboard::detail_url`) instead of rendering anything — this route only ever renders a synthesized view for a still-`Virtual`/`Skipped` occurrence. Otherwise dispatches by `series.item_type` to a new Task- or Event-flavored renderer (`project_tasks`/`project_events::handlers::render_series_occurrence_detail_page`), which builds a read-only view directly from `ItemSeries` + `occurrence_date` (`ProjectTaskSeriesOccurrenceView`/`ProjectEventSeriesOccurrenceView`) rather than reusing `ProjectTaskDetailView`/`ProjectEventDetailView` with a synthesized `Item` — the two views' embedded mutation URLs differ (occurrence-scoped vs. item-id-scoped), so they're separate Askama templates (`series_occurrence_view.html` etc.) visually mirroring the real ones, not a shared struct with an `Item`-or-not branch. A sibling `GET .../edit` route (`project_item_series_occurrence_edit_page`) follows the identical no-side-effect/redirect-if-materialized/dispatch-by-type shape for the edit form.
- Every mutation reachable from that page wraps materialize-first-then-write, per the plan: the checkbox (`hx-put` with `complete=true`) and the full edit form's "Save" both hit one new PUT route per item type (`.../occurrences/:ts/task` or `.../event`, since Task/Event forms have different shapes and axum's typed `Form<T>` extractor needs a concrete type — a single shared PUT route would have needed untyped body parsing) — `update_project_task_series_occurrence_form`/`update_project_event_series_occurrence_form` call `get_or_materialize_occurrence` then apply the edit via the existing `update_params_from_form`, then redirect to the real item's canonical page. "Adding a sub-item"/"adding a linked task" similarly hits a new POST route per type (`.../task-children`/`.../event-children`) that materializes first, creates the child, then redirects. Skip/Unskip reuse Stage B's existing routes unchanged (already occurrence-scoped, already redirect back to the calling page).
- Task/Event list rows and calendar entries for a still-virtual occurrence link to this new `GET` route instead of `hx-post`-ing the materialize route — in most templates this was a one-line change (drop `hx-post`, use the same URL string as a plain `href`, relying on `<body>`'s global `hx-boost`); in the two calendar templates that share one `<a>` between the materialized and virtual case (`project_events`/`project_dashboard`'s calendar pages), the `href` itself now resolves to the occurrence URL when set, falling back to the real detail link otherwise — no Rust struct fields changed.
- Materialized items keep their existing URLs (`/tasks/:id`, `/events/:id`) unchanged, confirmed live (see Verification below).
- Scope note: only the three mutations the plan explicitly named (checkbox, Save, add-sub-item/linked-task) got a deferred-materialization path. "Save as template" and "Promote to sibling of parent" — both present on the real item detail page — were deliberately left off the virtual-occurrence page: Promote is inapplicable by construction (a series occurrence is always top-level), and Save-as-template on a still-virtual occurrence wasn't asked for and would need its own materialize-first route; picking it up later is a small, isolated addition in the same shape as the other three, not a design gap.

Critical files: `src/web_ui/project_item_series/handlers.rs`, `src/web_ui/project_tasks/{handlers.rs,templates.rs}`, `src/web_ui/project_events/{handlers.rs,templates.rs}`, `templates/project_tasks/series_occurrence_{view,fields,detail_page,edit_page}.html`, `templates/project_events/series_occurrence_{view,fields,detail_page,edit_page}.html`, `templates/project_tasks/{virtual_row.html,calendar_page.html}`, `templates/project_events/calendar_page.html`, `templates/project_dashboard/{virtual_row.html,calendar_page.html}`, `src/main.rs`.

### Stage D — collapse duplicated rendering (implemented 2026-08-19)

- `ProjectOccurrence` (`src/service/item_series.rs`) gained `calendar_entry_id()`/`materialize_url(project_id)`/`skip_url(project_id)`/`unskip_url(project_id)`/`is_skipped()` methods, replacing four independent copies of the same format strings (Tasks calendar, Events calendar, Tasks flat-list virtual row, and `project_dashboard.rs`'s own trio of free functions). Every call site across `project_tasks/`, `project_events/`, and `project_dashboard.rs` now calls these instead of formatting the URL/id itself — one place to change if the route shape ever moves.
- Tasks' `CalendarTaskEntry`/`CalendarVirtualTaskEntry` pair collapsed into one `CalendarTaskEntry` struct (`Option<DateType>`/`is_virtual`/`is_skipped`/`is_current` fields), `CalendarDay` down to a single `tasks: Vec<CalendarTaskEntry>` (the former `virtual_tasks` field is gone), and `templates/project_tasks/calendar_page.html` down to one render block per day — following the shape `CalendarEventEntry`/`project_events/calendar_page.html` had already established, rather than two parallel per-day lists. `ProjectTaskRow` (a thin builder for the shared `components::row::Row` template) and `ProjectTaskVirtualRow` were deliberately **not** merged into one struct/template: `Row` unconditionally renders a delete button and other affordances (edit, duplicate, reschedule, subordinate-under picker) that assume a real, persisted item, and `Row` is shared by Events' and Simple Lists' rows too, which never have virtual occurrences at all — bolting virtual-occurrence fields onto it would ripple into screens that don't need them for the sake of a resemblance the calendar entries already share more directly. The list-row duplication that *was* addressed is the URL-building (previous bullet); the two structs' differing markup stays separate on purpose.
- Events' flat list view (`project_events_page`) now shows virtual/skipped occurrences too, via a new `project_events::render_rows_with_virtual` (mirroring `project_tasks::render_rows_with_virtual`) and a new `ProjectEventVirtualRow`/`templates/project_events/virtual_row.html`. Unlike Tasks (whose flat list shows only a Task-typed series' single current occurrence, by construction of that series' cursor), an Event-typed series has no cursor/"current" concept at all, so every occurrence in a forward window is shown — the same problem `project_dashboard.rs`'s flat list already solved for its own unbounded view, via a `VIRTUAL_OCCURRENCE_DEFAULT_WINDOW_DAYS`-style constant. `project_events::mod.rs` got its own `VIRTUAL_OCCURRENCE_WINDOW_DAYS = 90`/`virtual_occurrence_window(now)` pair (duplicated rather than shared, per this module's own established convention for these small per-screen helpers) with the same 90-day value.

Critical files: `src/service/item_series.rs`, `src/web_ui/project_tasks/{mod.rs,templates.rs}`, `src/web_ui/project_events/{mod.rs,handlers.rs,templates.rs}`, `src/web_ui/project_dashboard.rs`, `templates/project_tasks/calendar_page.html`, `templates/project_events/virtual_row.html` (new).
