Might want to keep it actually. When we show completed items, any recurring item doesn't show up because it was deleted.~~ Investigated and fixed. The "orphaned children" half was already not actually happening — `clone_children` (`src/service/items.rs`) re-parents every descendant onto the new occurrence (recursively, recomputing each one's `due_date` from its own `due_offset_days` against the new anchor) and deletes the old descendants as it goes, before the old parent itself is ever touched; this was already true going into this task and wasn't a live bug. The real gap was the second point: `update_item`/`update_team_item`'s recurrence branch unconditionally `repo.delete`d the just-completed parent row after cloning its children onto the successor, so a completed recurring item could never appear anywhere, including under "Show completed" — there was nothing left in the DB to show. Fixed by persisting the completed occurrence instead of deleting it (`repo.update`/`repo.update_team_item`, same row id, `complete: true`), so it now shows up like any other completed item wherever the existing `show_complete` toggle already applies (Tasks/Team Tasks/Events/Team Events list pages, and the dashboard's due-date presets, all of which already had this filter and needed no changes). One new failure mode this opened up: since a completed item's read-only detail view keeps a checkbox that can flip it back to incomplete, and the archived row still has its original `recurrence`/`recurrence_basis`, re-completing it (e.g. via the checkbox) would otherwise re-fire `next_recurrence` a second time and spawn a duplicate "next occurrence" alongside the one already created by the original completion. Closed by a new `archive_recurrence` helper (`src/service/items.rs`) that clears `recurrence`/`recurrence_basis` on the archived row right before it's persisted — `next_recurrence` requires a parseable pattern to fire at all, so the archived row is permanently inert as a recurrence source even if toggled complete/incomplete/complete again; verified live via the JSON API that doing exactly that leaves the item count unchanged (no duplicate spawned). Updated the two existing unit tests that asserted the old `expect_delete` behavior to assert `expect_update`/`expect_update_team_item` with a cleared recurrence instead (`cargo test`, 96/96 passing); live-verified end-to-end against a scratch server: completing a recurring top-level item with an offset child leaves the old row in the DB as `complete=1, recurrence=NULL, parent_item_id=NULL`, the new occurrence as `complete=0` with the advanced due date and the re-parented child, and the old child row gone entirely.
