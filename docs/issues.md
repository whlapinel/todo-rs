3. Add a link to the series from an item's detail page when that item is a materialized series occurrence; add a "skipped" indicator and an "unskip" action wherever an occurrence is shown. **Medium — the deletion-cleanup half was actually only half-done, not fully done as previously noted here; the missing half is now fixed (2026-08-16).** The original concern ("if a user materializes an occurrence and then deletes it, the series occurrence should also be cleaned up... so it either points to an existing item or `is_exdate` is checked") was resolved back in Stage 6 of the item_series redesign (`unlink_deleted_item_occurrence`, called from `delete_project_item`): deleting a materialized item's row does mark its occurrence exdate on every delete path. But this note previously claimed that closed the concern out fully — it didn't: `unlink_deleted_item_occurrence` never advanced the series' `cursor_date` the way its explicit-Skip-button sibling (`skip_occurrence`) does, an asymmetry that predates Stage 10a's cursor-derived `current_occurrence_date`/strict-in-order-settlement invariant and was never retrofitted once that landed. Net effect: deleting the item behind a series' *current* occurrence left the series permanently stuck believing that (now itemless) date was still current, rejecting every later occurrence — including ones already materialized and worked on — as "out of order". Found via a real prod-DB bug report (two daily chore series each frozen for six days after their first occurrence's item was deleted) and fixed by making `unlink_deleted_item_occurrence` advance the cursor exactly when the deleted occurrence was current, mirroring `skip_occurrence` (`src/service/item_series.rs`). What's still genuinely open, unaffected by this fix: (a) a materialized item's detail page has no link back to its series (`ItemSeriesRepo::find_occurrence_by_item_id` already exists as the reverse lookup — this is mostly a template + one query away); (b) there's no visible marker distinguishing a skipped (exdate) date from one that was simply never reached, anywhere in the UI; (c) no "unskip" action exists (would just need a new handler clearing an `item_occurrences` row's `is_exdate`/deleting the exdate row).

The "orphaned children" half was already not actually happening — `clone_children` (`src/service/items.rs`) re-parents every descendant onto the new occurrence (recursively, recomputing each one's `due_date` from its own `due_offset_days` against the new anchor) and deletes the old descendants as it goes, before the old parent itself is ever touched; this was already true going into this task and wasn't a live bug. The real gap was the second point: `update_item`/`update_team_item`'s recurrence branch unconditionally `repo.delete`d the just-completed parent row after cloning its children onto the successor, so a completed recurring item could never appear anywhere, including under "Show completed" — there was nothing left in the DB to show.
