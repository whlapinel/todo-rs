Ranked easiest → hardest (re-ranked 2026-08-15 after the item_series redesign completed — see docs/recurring-events-virtual-occurrences-rough-plan.md). Two items previously listed here were already implemented and have been moved to archived-features.md: "Simple lists shouldn't have assignment UI" and "only show the current materialized occurrence of a task series in the flat task list" (the latter had been mistakenly re-added as open by a doc-sync commit after it already shipped — see that archive entry's correction note).

1. Need to be able to edit series in the UI (create-only today). **Easy** — `UpdateItemSeries` already exists end-to-end (Smithy/service/CLI/MCP, Stage 7b) and is unused only by the web UI. A `GET/PUT /web/projects/:project_id/series/:id/edit`-style page mirroring the existing `/series/new` form (`src/web_ui/project_item_series/`, `templates/project_item_series/new_page.html`) is the whole task — no schema or service-layer work needed.

2. Events shouldn't have any concept of "completeness" (no checkbox, no Done/Not done, no "Show completed" filter) — same treatment Simple items already got. **Now easier than previously scoped.** The blocker `docs/event-complete-removal-plan.md` was written around — "completion is the only thing that advances a recurring Event's date, so removing it needs a replacement trigger" — no longer applies: item-level Event recurrence was retired entirely in the item_series redesign's Stage 10 (`8797ac9`), so an Event's `complete` field no longer triggers anything (recurring Events now live on `item_series`, advanced by materialization/range-browse, independent of completion). **`docs/event-complete-removal-plan.md` is stale and should be re-read/rewritten before starting** — its "auto-advance on read" design solves a problem that no longer exists; the actual remaining work is likely just: strip the checkbox/Done-label/"Show completed" filter from `project_events/` templates and add an `Item::validate()` rejection for `complete: true` on `ItemType::Event`, mirroring the already-shipped Simple-item precedent (see archived-features.md item 7). Worth a quick recheck of team-item completion-guard interactions (`update_team_item`'s assignee-only-completion check) before starting, since Events structurally never carry `team_assignment` today.

3. Need to be able to delete series in the UI (and at the API layer — `DeleteItemSeries` doesn't exist yet, unlike `Update`). **Medium** — this was deliberately deferred at Stage 4a and again at Stage 6 ("the same materialized-occurrence question stage 6 already defers") specifically because it needs a real design decision: does deleting a series cascade-delete its materialized `items` rows, orphan them, or refuse while any exist? Needs a short design pass (`AskUserQuestion` or planning session) before the usual full touch-point sweep (Smithy + service + web UI + CLI + MCP).

4. Activity log should also include non-point completions and allow reversal. **Medium** — unrelated to the item_series work. Today `activity_log` is scoped to points/completion events on team-backed-project items only (CLAUDE.md's Points section); logging *every* completion (including personal-project and non-points team items) needs a new log-entry shape or a nullable-points variant of the existing one, plus reversal semantics for a completion that never had points to reverse (currently `reverse_entry` only ever un-awards points — un-completing the item itself is a separate, already-existing action).

5. Individual and Mass rescheduling ("skip current" without completing). **Medium-hard, but fully designed already** — see `docs/scheduled-catchup-plan.md`, which already resolved every open design question (cross-project screen vs. dashboard preset, non-recurring items land on "today, same time", Tasks-only for now). This is scoped as pure implementation against that doc, not a redesign — but it's still a new cross-project screen plus a new repo method plus a bulk-action pattern this codebase doesn't have a precedent for yet (closest analog: the CSV importer's best-effort-per-row model), so it's a real multi-file feature, not a quick win.

6. Due date should be secondary for tasks (mirroring Todoist's `scheduled_date`-primary model), and/or due date should follow the same recurrence rules as scheduling. **Hardest, explicitly deferred already** — see CLAUDE.md's Scheduled start/end section ("Deferred / partially implemented"): touches dashboard preset grouping/sorting, `list_due`/`prl items due`, and web-UI field-prominence ordering across every screen. Also tangled up with the still-unresolved "floating calendar date" display tension noted in the same CLAUDE.md section (bare dates anchor to an instant computed from the submitter's timezone rather than floating with the viewer) — worth resolving that design question first, since this feature would touch the same date-display code paths. Not scoped or planned in any doc yet; would need its own planning pass before implementation.
