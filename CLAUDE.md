# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

**What belongs here.** This file explains *why* the code is shaped the way it is — decisions, rejected alternatives, invariants, and cross-cutting behavior a reader can't recover by reading one file. It deliberately does **not** inventory what the filesystem already answers (which repo traits, service modules, or screens exist — run `ls`). Two rules keep it from rotting: **state each fact in exactly one section** and cross-reference it by name from everywhere else, and **update the owning section when you change an invariant or add a feature area** (see the Touch-Point Checklist). Restatement is what actually rots — the `Item` field descriptions survived the `ItemType` split unchanged, and wrong, in five separate sections.

## Working style

Do not use sub-agents (the `Agent` tool, including `Explore`/`general-purpose`/etc.) for work in this repo — do research and implementation directly. This applies even for "just research, no edits" tasks like surveying existing patterns before implementing a feature.

## Git

Do not add `Co-Authored-By` trailers to commits.

Before creating any commit, run plain `cargo fmt` (no path arguments) from the repo root, then stage any resulting formatting changes as part of the commit. Keeping the whole repo uniformly formatted this way means there's never a partially-formatted file left for a later scoped `rustfmt <file>` or `cargo fmt -- <file>` invocation to collide with — which is what caused repeated formatting breakage in the past (a scoped invocation on a crate-root file like `src/main.rs` reformats every file transitively reachable through `mod` declarations, producing a huge unrelated diff). Always use plain `cargo fmt` with no arguments; never invoke the `rustfmt` binary directly or pass specific files to `cargo fmt --`.

See `Taskfile.yml` for the full task list (`codegen`, `run`, `build`, `check`, `web-styles`, `cli-build`, `cli-install`) plus `cargo test` for the Rust test suite.


For UI-only changes (no Smithy or Rust changes): edit `templates/*.html`, then `cargo build` picks it up (Askama embeds templates at compile time — there's no separate template-build step). If Tailwind classes changed, also run `task web-styles`.

**Don't use Playwright (or any other browser-automation tool) to click-through/verify UI changes** — the user does that verification themselves; it burns tokens for no benefit here. Verify with `cargo build`/`cargo test`/`task check` and a careful read of the template/handler diff instead, and say so explicitly if live-in-browser behavior can't actually be confirmed that way.

## Architecture

### Full Pipeline

```text
model/src/main/smithy/*.smithy
        │  (task codegen / ./gradlew :model:assemble)
        ▼
todo-server-sdk/          ← generated Rust crate (DO NOT EDIT)
todo-client/              ← generated Rust client crate (DO NOT EDIT)
todo-typescript-client/   ← generated TS client (DO NOT EDIT) — codegen output only, no consumer
        │
        ▼
src/main.rs                    ← axum server wiring, route registration, background sweeps
src/json_api/                  ← JSON API handlers backing the Smithy service
src/web_ui/ + templates/       ← server-rendered UI (Askama + htmx)
src/service/                   ← business logic shared by both presentation layers
src/storage/                   ← repo traits + their SQLite implementations
src/domain/                    ← plain structs, no framework coupling
todo-cli/src/                  ← prl CLI (standalone crate, uses generated todo-client)
```

There is no browser-side TypeScript client or SPA — the UI is server-rendered (see Web UI below). `todo-typescript-client/` is still generated by `task codegen` but nothing in this repo builds or consumes it.

### Smithy Model → Generated Code

The `.smithy` files in `model/src/main/smithy/` define the full API contract. `User` is the only Smithy `resource`; every item is owned by exactly one **`ProjectItem`** — identifiers `{projectId, itemId}`, at `/projects/{projectId}/items/{itemId}`. This replaced the original `User → Item` (personal) and `TeamItem` (team-scoped) resources, retired in Stage C3 of `docs/archived/project-abstraction-plan.md`: every project is either personal (no backing team) or team-backed, so a single project-scoped resource covers both. `Team` and `Project` are plain operations, not resources — team CRUD under `/users/{userId}/teams`, project CRUD under `/users/{userId}/projects`. Items nest via `parentItemId`.

The `items` SQLite table still carries a nullable `user_id` alongside `project_id` — the pre-Project-abstraction column, kept because `ItemRepo` still exposes personal-shaped methods (see Storage Layer). `items.team_id` was the team-scoped counterpart; Stage 6 of `docs/archived/team-id-removal-plan.md` dropped it once `project_id` became the sole scoping key for team-backed items too.

smithy-rs (a Gradle composite build via the `smithy-rs/` git submodule) generates `todo_server_sdk::input/output/error::*` (typed structs per operation), `PeoplesRepublicOfLists` (the tower `Service` — HTTP routing and serde handled automatically), and `PeoplesRepublicOfListsBuilder` (wires async handlers to operations). Handler signature:

```rust
async fn op_name(input: input::OpInput, server::Extension(repo): server::Extension<Arc<dyn Repo>>)
    -> Result<output::OpOutput, error::OpError>
```

The service is annotated `@httpBearerAuth`. This affects **client** codegen only — it generates `Config::builder().bearer_token(...)` and a scheme that auto-attaches the `Authorization: Bearer` header on `todo-client`. Server-side codegen has no handling for HTTP auth traits at all, so adding or removing the trait never changes generated server code. Actual token verification is, and must remain, hand-written in `src/auth.rs`; the trait standardizes how the client carries the credential, not how the server validates it.

The router routes by segment count plus literal specificity, so sibling paths at different depths (`/series/{id}` vs `/series/{id}/children` vs `/series/{id}/children/{childId}`) can't collide. On the axum side, API routing uses catch-alls (`/projects/*path`), so a new sub-path under an existing prefix needs no new route registration.

### Server (`src/main.rs`)

Handlers receive dependencies via `server::Extension` (injected through `tower::ServiceBuilder` layers). The Smithy service is nested under `/api`; the server-rendered UI under `/web`; `/` redirects to `/web/tasks`. Compiled CSS/JS is served from `static/` via `ServeDir` at `/web/static`. Auth mode is selected at startup via `TODO_AUTH_MODE` (see Auth).

`main.rs` also owns two **background sweeps**, both spawned only when their feature is configured and both sleeping first rather than firing at boot (a sync-immediately-then-sleep shape would mean a thundering-herd fetch across every subscription on every restart): a 15-minute calendar sync (see Calendar subscriptions & iCal import) and a 60-second push-reminder sweep (see Reminders, notifications & push). The `/web/*` router carries a `DefaultBodyLimit` sized off `service::attachments::MAX_ATTACHMENT_SIZE_BYTES` — see Attachments & comments for why that coupling matters.

### Auth (`src/auth.rs`)

Two modes, selected by `TODO_AUTH_MODE`:

- **`internal`** (default) — full Google OAuth + JWT flow. Requires `TODO_GOOGLE_CLIENT_ID`, `TODO_GOOGLE_CLIENT_SECRET`, `TODO_JWT_SECRET`. Mounts `/auth/google`, `/auth/callback`, `/auth/logout`, `/auth/me`, `/auth/token`. `/auth/token` issues a long-lived JWT for CLI/MCP clients.
- **`caddy`** — also requires `TODO_JWT_SECRET` (to verify Bearer tokens). Mounts `/auth/me` and `/auth/token`. `caddy_header_middleware` accepts identity two ways: (1) the `x-token-user-email` header injected by caddy-security for browser sessions — trusted as-is, no signature check, because only caddy-security can set it; or (2) `Authorization: Bearer <jwt>` for CLI/MCP requests, verified against `TODO_JWT_SECRET` exactly as `internal` mode does. Set `TODO_DEV_EMAIL=you@example.com` to bypass the header check for local dev without Caddy.

  **Cross-repo dependency:** for a Bearer-token request to reach path (2) at all, the edge proxy must not intercept it first. caddy-security's `authorize with mypolicy` would otherwise 302-redirect *any* unauthenticated request — including ones carrying our own JWT, which it doesn't recognize — to its login portal. The home-server repo's `Caddyfile.local` gives this app's host its own site block with a matcher that skips `authorize` for requests carrying `Authorization: Bearer`. If that Caddyfile change is ever reverted, path (2) becomes unreachable in production even though this code still supports it.

In both modes `AuthUser { user_id }` is injected into request extensions.

**`/web/*` auth and the login page:** `build_web_router()` holds every protected `/web/*` route; a separate `build_public_web_router()` holds only `GET /web/login`. Only the protected router gets the auth layer, and the two are `.merge()`d *before* being nested under `/web` — otherwise the login page would go through the check that redirects it straight back to `/auth/google`. `internal` mode redirects unauthenticated `/web/*` requests to `/auth/google` rather than returning a bare 401; `caddy` mode 401s, since auth is expected to happen at the edge.

One narrow bootstrap exception lives here: `caddy_header_middleware` promotes a user to admin of exactly one production team's **backing project** (`TODO_BOOTSTRAP_ADMIN_TEAM_ID` names a *team*, matching caddy-security's own role model; `sync_bootstrap_project_admin` resolves it to that team's project) when their `x-token-user-roles` contains `authp/admin` and that project has zero active admins. Gated on the project's admin count, not the user's current role, so it fires at most once per project and goes permanently inert afterward — a deliberate in-app demotion is never silently undone. Every other project's roles are managed entirely in-app (see Per-team roles & admin bootstrap).

### Storage Layer (`src/storage/`)

`sqlite` is the sole implementation — the `memory`/`dynamo` backends this section used to describe were removed once nothing exercised them. Every repo trait lives in `src/storage/sqlite/mod.rs` (not a separate top-level `mod.rs`), each `#[cfg_attr(test, mockall::automock)]` so services can be unit-tested against mocks, with one implementation file per trait beside it. `storage::attachment_store::AttachmentStore` is the one storage trait deliberately *outside* that file — it stores bytes, not rows (see Attachments & comments).

Two things about the traits that reading them won't tell you:

- **`ItemRepo` carries two method shapes side by side.** The original personal-`Item`-shaped methods (`get`, `list`, `create`, `update`, `list_due`, `list_templates`) and the project-shaped ones (`get_by_project`, `list_by_project`, `update_by_project`, `list_due_by_project`, `list_templates_by_project`) that every `ProjectItem` request — personal or team-backed — actually goes through. A third `TeamItem`-shaped set existed alongside them until Stage 6 of `docs/archived/team-id-removal-plan.md` removed it. The personal-shaped half is still live because `src/service/items.rs` still uses it.
- **Role and points authority sits on `ProjectRepo`** (`member_role`, `set_member_role`, `count_active_admins`, `add_project_points`), not `TeamRepo` — those are two genuinely different authorities, see Per-team roles & admin bootstrap.

**Schema management is split in two.** The baseline `CREATE TABLE IF NOT EXISTS`/`CREATE INDEX IF NOT EXISTS` statements in `create_pool()` always reflect the *current* full schema, so a fresh DB is correct from the start and never runs a migration. Changes to already-deployed DBs go through `src/storage/migrations/` — a versioned `Migration` trait (`version()`, `name()`, `up()`), one file per migration, registered in `all_migrations()` and run once at startup by `run_migrations(&pool)`, which tracks applied versions in a `_migrations` table and runs each in its own transaction. Adapted from a sibling project's system with one addition: SQLite's `ALTER TABLE ... ADD COLUMN`/`DROP COLUMN` have no `IF NOT EXISTS` form, so every migration guards its `ALTER TABLE`s with `column_exists()` (`PRAGMA table_info`) — necessary because a DB that already has the target column (a fresh DB whose `CREATE TABLE` includes it, or one migrated under the old pre-`_migrations` inline-ALTER approach) must not error on first run.

An applied migration is history, not live design: don't retrofit it when the model changes. A column an old migration still writes has to stay declared in the baseline `CREATE TABLE` even after the field is removed from the domain (`item_series.template_item_id` is the standing example).

### Domain Models (`src/domain/`)

Plain Rust structs, no framework coupling — this section owns the shape of `Item`; every other section below refers to fields by name rather than restating where they live.

`Item` (`src/domain/item.rs`) is a thin envelope — `id`, `user_id`, `project_id`, `name`, `description`, `has_children`, `item_type: ItemType` — plus a set of `Option`-returning delegation methods (`due_date()`, `complete()`, `parent_item_id()`, `priority()`, `series_id()`, `event_type()`, `google_event_id()`, ...) that read through to whichever payload `item_type` holds. **Every field that only makes sense for some kinds of item lives inside `ItemType`, not flat on `Item`.** This is the end state of `docs/archived/item-kind-split-plan.md` (Stages 0–8, complete), which moved `complete`, `parent_item_id`, `series_id`, `google_event_id`, and `calendar_subscription_id` off a flat `Item` one at a time. The motivation: a flat `Option` field the wrong kind could still theoretically set is a runtime invariant enforced only by `validate()`; putting the data inside the variant makes the invalid state unconstructable — a `Task` has nowhere to put an Event's `google_event_id` because `TaskItem` has no such field, not because a check rejects it.

Two enums, easy to confuse:

- **`ItemKind`** — plain, `Copy`, data-free (`Task`/`Event`/`Template`/`Simple`). Used wherever only the *discriminant* is needed: DTOs, SDK conversion, web_ui type guards, the "Kind" badge, the CLI's `--item-type` flag. Read off an item via `Item::kind()`.
- **`ItemType`** — its data-carrying counterpart, what `Item::item_type` actually holds: `Task(TaskItem) | Event(EventItem) | Template(TemplateItem) | Simple(SimpleItem)`.

Three small structs are shared by reference across payloads rather than duplicated: `Schedule` (`due_date`/`has_due_time`/`scheduled_date`/`has_scheduled_time`/`scheduled_end_date`/`has_end_time` — see Scheduled start/end), `Recurrence` (`pattern`/`basis`, both vestigial-display-only, plus `due_offset_days`, fully live — see Recurrence), and `TeamAssignment` (`assigned_to_user_id`/`points`, top-level-only — see Points). Since Stage 3 of the templates-assignment work (see Events) `TeamAssignment` is no longer Task-exclusive: a *root* `TemplateItem` carries one too, stamped onto the event-trigger/"Use" flow's new parented task at instantiation time — see that field's own doc comment for why a nested template child structurally can't. The payloads:

- **`TaskItem`** — `parent_item_id`, `schedule`, `recurrence`, `team_assignment`, `source_event_id`, `source_template_id`, `priority`, `complete`, `series_id`. The only kind that can be completed, hold a priority, or reference a source Event; the only kind whose `team_assignment` is ever actually live on a real item (a Template's is a spec for what to stamp onto a future task, not a live assignment itself).
- **`EventItem`** — `schedule`, `recurrence`, `event_type`, `series_id`, `google_event_id`, `calendar_subscription_id`. No `parent_item_id`: an Event structurally cannot be a child of anything.
- **`TemplateItem`** — `parent_item_id`, `schedule`, `recurrence`, `event_type`, `team_assignment`. Genuinely nests (a template's child subtree is itself Template-typed rows), so it carries a parent despite a *root* template never having one; `team_assignment` is likewise only ever set on a root template — see Events.
- **`SimpleItem`** — `parent_item_id` only. A bare checkable name: no schedule, no recurrence, no `event_type`, no completion concept.

Two marker traits, `HasSchedule`/`Completable`, exist for the rare function handed a payload struct directly rather than an `Item`. Both are `#[allow(dead_code)]`: every current caller (list filters, the occurrence merge, the calendar fan-out) goes through `Item`'s delegation methods instead. That's not evidence they're pointless — they're the intended seam if a genuinely kind-blind consumer appears; drop the attribute then, not before.

`Item`'s delegation methods stay `Option`-returning even when a caller already knows the concrete kind. Handing back the concrete struct was evaluated and rejected in Stage 7 of that plan: the field is still genuinely optional for a guaranteed kind (a `Task` can legitimately have `parent_item_id: None`), so there was no "unwrap a should-be-`Some`" pattern to eliminate. The per-screen kind guards (`require_task`/`require_event`/`require_simple`/`require_project_template`) keep their plain `Item -> Item` signature for the same reason.

`Item::deadline_from_offset(root_deadline, tz_offset_minutes)` is the domain-level decision for a child's offset-driven deadline: `due_offset_days.map(|n| end_of_day(root_deadline + n days))`, `None` when no offset is set. Pure and unit-tested in isolation from its callers.

`Item::validate()` is where the cross-field rules that survived the split are enforced — points on a child, name/description length, `priority` in 1–4, non-positive `due_offset_days`, `parent_item_id` and `source_event_id` mutually exclusive. Every write path calls it. Note what is *not* there: rules the split made structural (a Task has no `event_type` field to reject) and rules that need more than one item or a repo lookup (the scheduled-window ordering check, the completion guards) live in `src/service/`, not here.

Other domain modules follow the same "plain struct + doc comment" shape and are owned by their feature sections below: `item_series`, `reminder`, `push_subscription`, `comment`, `attachment`, `calendar_subscription`, `activity_log`, `project`, `team`, `user`. `User::personal_project_id` records the one project a user can never delete or attach a team to (`service::projects` enforces both), backfilled lazily for users who predate the column.

### Recurrence — retired at the item level (`src/domain/recurrence.rs`)

Item-level recurrence (a completed item spawning its own successor) was retired in Stage 10 of `docs/archived/recurring-events-virtual-occurrences-rough-plan.md`: a one-time migration moved every recurring item onto an `item_series`, and the mechanism's code — `Item::next_recurrence`, `clone_children`, `archive_recurrence`, `repoint_source_event_tasks`, and the `recurrence`/`recurrenceBasis` Smithy fields — was deleted. Anyone wanting a recurring item now creates an item series (see below), not an item with a recurrence string.

`src/domain/recurrence.rs` itself is **not** retired: its English-phrase parser (`every N days/weeks/months/years`, `every month on the Nth`, `every [weekday]`), its `advance_once` stepper, and `occurrences_between` are exactly what item series use. What's gone is only `Item`-level usage.

The domain `Recurrence` struct keeps `pattern`/`basis` and their accessors, deliberately, for two historical-display purposes: a Template's "↻ repeats" badge (an inert copy taken at "Save as template" time, from before the retirement) and any already-completed legacy row predating the migration. Nothing can populate them again — no Smithy field, CLI flag, MCP parameter, or form input carries them, so every create/update path constructs `Recurrence { pattern: None, basis: None, due_offset_days: ... }`.

**`due_offset_days` is unaffected and stays fully live** — it was never recurrence-specific. A child item (`parentItemId` set) or an event-linked task (`sourceEventId` set) carries days from its top-level item's or linked event's anchor date; negative is before, positive after. `Item::validate()` rejects a *positive* value outright ("due offset days cannot be positive") — it never made sense for a sub-item to be due after the thing it supports. Every caller therefore presents this as **"days before due"**, a non-negative number negated before it reaches the wire: the web UI's offset field, `prl items add --days-before-due`, and the MCP tools' `daysBeforeDue`. The stored/wire sign convention is unchanged; it just can't be written positive anymore. Rows written before this check landed may still carry a stale positive value — the check guards new writes only, there's no migration.

Two things drive the offset→due-date recompute:

- `sync_offset_children`/`sync_source_event_tasks` (`src/service/items.rs`) fire on **any** plain edit that moves a top-level item's or Event's anchor date (`due_date.or(scheduled_date)`), independent of recurrence. Children are updated **in place** (same id), and a child with no `due_offset_days` is left untouched rather than cleared — it isn't derived from the parent, so a parent edit shouldn't touch it.
- `copy_template_children`/`copy_children_as_template` — the Templates screen's "Use" flow and the event-trigger mechanism (see Events).

### Item series & sub-items (`src/domain/item_series.rs`, `src/service/item_series.rs`, `src/storage/sqlite/item_series.rs`)

An **`ItemSeries`** is what replaced item-level recurrence: a recurrence rule plus an `anchor_date` and static fields, owned by a project. It deliberately has **no date of its own** — an occurrence date is computed against the rule, so a series with a hundred future dates is one row, not a hundred. `item_type` is restricted to `Task`/`Event` and is **immutable after creation**: flipping a series' kind would leave already-materialized occurrences at the old kind while future ones materialized at the new one, so `update_series` rejects a mismatch and the edit dialog renders Kind read-only.

**Virtual vs. materialized is the central idea.** An occurrence date with no `item_occurrences` row is *virtual* — it renders in lists and calendars and can be edited, skipped, or completed, but no `items` row exists for it. `get_or_materialize_occurrence` creates one only when a change is actually persisted, never on view or "touch". `ItemOccurrence` records the two post-virtual states: materialized (`item_id` set) or skipped (`is_exdate`, the EXDATE equivalent). `list_occurrence_states_for_project` is the single query every screen builds on, replacing an older per-screen "query real items and virtual dates separately, then merge by hand" pattern. `Item::series_id` is the reverse link on a materialized occurrence — set once, at creation, only by `get_or_materialize_occurrence`, and carried forward unchanged on every update the way `project_id` is; no Smithy field, CLI flag, or MCP parameter can set or clear it, because an item's series membership never changes after creation. It is additive to, not a replacement for, `find_occurrence_by_item_id` (via `item_occurrences`), which several write-path gates still use.

A Task series also carries a **`cursor_date`** — the most recent occurrence it has settled (completed or skipped), advanced forward-only, never user-settable. It's what lets `require_current_occurrence`/`require_cursor_occurrence` reject completing or uncompleting anything but the series' current occurrence, and it's meaningless (always `None`) for an Event series, which has no completion concept. `basis` (`None`/`"COMPLETION"`/`"DUE_DATE"`) selects what the next occurrence is measured from and which date field a materialized occurrence lands on; `validate_series_basis` enforces that both non-default values are Task-only.

**Assignment rotation.** A Task series on a team-backed project may name a *rotation* instead of a fixed assignee — `assigned_to_user_id` and `rotation_user_ids` are mutually exclusive (`resolve_series_assignment`), and members live in their own table (`list_rotation_members`), not on `ItemSeries`. The rotation is **stateless**: whose turn it is is computed fresh from the occurrence's index in the series (`occurrence_index` → `rotation_assignee`, `index % len`), never stored or advanced. That's what keeps it correct for any occurrence — past, current, or far future — with no cursor of its own and no repair needed when membership changes. An explicitly empty `rotationUserIds` is rejected rather than read as "clear it" (omit it instead), matching the `item_type`/`event_type` omission convention. A root `TemplateItem` mirrors this shape (`template_rotation_members`, `resolve_template_assignment_input`, the same shared `rotation_assignee`) but can't reuse `occurrence_index`'s calendar math — see Events for why it counts prior task firings instead.

**`ItemSeriesChild` — series sub-items.** Lead-time preparation work every occurrence of a Task series carries: a "Party, every Nov 1" series owns "book venue" 30 days before and "send invites" 14 days before. A definition is a plain row owned by the series — deliberately *not* a child `ItemSeries` (an earlier attempt modeled it that way and was reverted: a sub-item has no recurrence, anchor, or cursor, so every one of those fields had to be nullified or delegated, and every cursor codepath needed an exemption) and *not* an `ItemType::Template` child (a project-library artifact with its own lifecycle, editable or deletable out from under the series). It replaced `ItemSeries::template_item_id`, removed outright with no migration because it fired at materialization time — long after the lead-time warning it was meant to give. The definition set is flat; a materialized occurrence can still be given ordinary sub-items by hand.

The same virtual/materialized model applies one level down, with two deliberate differences: **there is no sub-item Skip**, so `series_child_occurrences` needs no `is_exdate` and its `item_id` is non-optional (a row exists only once materialized), and its `occurrence_date` is the **parent series' cycle date**, not the sub-item's own due date — which keeps the identity stable when a definition's `days_before` is edited. `fan_out_child_occurrences` turns already-computed parent occurrences into view rows (taking them rather than recomputing, so it never had to change `list_occurrence_states_for_project`'s signature at any call site).

Three rules follow from the design and are worth knowing before touching any of it:

- **Materializing a sub-item materializes its parent occurrence first**, because a materialized sub-item is a *structural child* (`parent_item_id`) of the occurrence's item. That cost was accepted deliberately: it buys `sync_offset_children`, `has_incomplete_children`, and the existing nested rendering instead of reimplementing all three. The resulting invariant — **a still-virtual parent can only ever have still-virtual sub-items** — is what keeps the nested-rendering cases small. The materialized item deliberately does *not* get `series_id`: that field means "this item *is* an occurrence", and a sub-item is a child of one.
- **Every sub-item blocks its occurrence's completion**, virtual ones included (`require_child_occurrences_materialized`). There is no waiver — a Skip action was considered and rejected for pre-empting the per-sub-item "non-blocking" flag that is the principled way to say a sub-item doesn't block (not yet built). The guard only covers the never-materialized case; a materialized-but-incomplete sub-item is an ordinary structural child that `has_incomplete_children` already blocks. The error names the outstanding sub-items, since the row checkbox posts straight into a materialize-and-complete handler and the rejection is all the user sees.
- **Deleting a materialized sub-item's item reverts that occurrence to virtual — it reappears**, because the definition still exists and the row is recomputed on the next render (mirroring `delete_occurrence` vs `mark_exdate` one level up). The way to be rid of a sub-item is to delete the *definition*.

`days_before` is stored non-negative per the app-wide convention (see Recurrence) and negated into `due_offset_days` only at materialization, so `validate`'s non-positive rule holds by construction. **Known gap, inherited rather than introduced:** `create_item` recomputes an offset-driven child's `due_date` from the top-level ancestor's `due_date` and never its `scheduled_date`, so a sub-item materialized under a *scheduled*-basis occurrence lands undated. Visibility before materialization is unaffected. Tracked in `docs/issues_and_features.md`; the same is already true of every hand-added sub-item on such an occurrence.

**Cascades and cleanup.** `delete_series` drops the series' occurrence rows, its child definitions and their occurrence rows, but never touches `items` — orphan, not cascade, so every already-materialized occurrence survives as a plain standalone item (the treatment `unlink_source_event_tasks` gives a deleted Event's linked tasks). `delete_series_child` is the same shape one level down. `unlink_deleted_item_occurrence`/`unlink_deleted_child_occurrence` must be called everywhere an item is deleted — including the *recursive* child-delete loops inside `items::delete_item`/`team_items::delete_team_item`, not just `project_items::delete_project_item`; the regression test `delete_project_item_unlinks_a_series_materialized_descendant` exists for the bug that arises when that's missed.

**Surfaces.** Virtual rows carry composite ids — `{series_id}:{occurrence_ts}` for an occurrence, `child:{child_id}:{parent_occurrence_ts}` for a sub-item — both parsed by `parse_virtual_row_id`; the literal `child:` prefix (not a segment count) is what keeps the three id shapes unambiguous, since a real item id and a definition id are both bare UUIDs. The calendars widen their occurrence query by `max_child_lead_days`, because a sub-item buckets on its *own* date while the fan-out derives that from the parent cycle — without it, exactly the lead-time rows this feature exists for would fall outside the visible range. The web Sub-items panel is edit-only (the New dialog has no `series_id` for children to belong to yet). JSON API operations live under `/projects/{projectId}/series/{seriesId}/children`, with no `Get` for a single definition — the set is small and always read whole, and `sortOrder` is a server-maintained append counter that stays off the wire. CLI/MCP detail is in `docs/prl-user-guide.md`, `todo-cli/CLAUDE.md`, and `mcp-server/CLAUDE.md`.

### Events and template triggers (`src/service/items.rs`, `src/service/team_items.rs`)

An item's kind (`ItemKind`, carried as the `ItemType` variant — see Domain Models) replaced a separate `is_template: bool` plus what would have been an independent `is_event: bool`; both answered "what kind of thing is this row", so they're one field rather than two that can drift. `Task` is the default; an `Event` is display-primary on its scheduled window rather than its due date; a `Template` is a library artifact that only `service::templates::create_template` may produce — `create_item`/`update_item`/`create_team_item`/`update_team_item` reject `itemType: TEMPLATE` unless the item's parent is itself a Template.

That last clause narrowed in Stage 4 of `docs/archived/typed-item-params-plan.md`; the guard used to reject `TEMPLATE` outright. What it protects is the **library**, which is root-only (`ItemRepo::list_templates_by_project` filters `parent_item_id IS NULL`) — a template *child* is an ordinary subtree row, and `create_item` had always minted those anyway by coercing any child of a Template to `Template`. Rejecting the honest spelling of a request the coercion already granted bought nothing, and hid two drifts: `create_team_item` had no such coercion, so a template child on a team-backed project was created as a plain `Task`, and `update_item` had none either, so the Templates screen's own child edit (which passed `itemType: TASK`) silently demoted a personal one on its first save. All four functions now carry the coercion, and `service::item_input::NewTemplate`/`EditTemplate` — whose `parent_item_id` is a non-optional `String` — are how the screen says what it means.

`ItemType` is this model's **one genuine Smithy `enum`** (`TASK`/`EVENT`/`TEMPLATE`/`SIMPLE`). Every other finite-valued field (`eventType`, a series' `basis`, an import `format`) is a plain `String` compared by literal at the Rust layer with no Smithy-level validation. The exception is deliberate: smithy-rs generates a real closed enum server-side (rejecting unrecognized strings with a `ConstraintViolation` at the deserialization boundary, so invalid values never reach handler code) and an open one client-side with an `Unknown` catch-all for forward compatibility. `src/json_api/mod.rs`'s `to_domain_item_type`/`to_sdk_item_type` convert at the boundary.

**`event_type`** (on `EventItem` and `TemplateItem`; read via `Item::event_type()`) is a plain unvalidated string with a dual meaning depending on which it's set on:

- On an Event, it's "this occurrence's category" (e.g. `"rain"`).
- On a Template, it's "fire me when a matching item is created."

No other kind can carry one **structurally** — `TaskItem`/`SimpleItem` have no such field, so this needs no `validate()` check and has none (the test `task_item_type_has_no_event_type_slot` documents exactly that). This is the clearest payoff of the `ItemType` split: what used to be a runtime rejection is now an unrepresentable state. The Tasks and Simple-list screens expose no `event_type` field at all; only the Events and Templates screens do. The CLI and MCP tools still accept it as a plain parameter, and the server is the enforcement point — see Cross-kind fields at the boundary below for what "enforce" now means.

#### Cross-kind fields at the boundary

Everything above is about what a kind can *hold*. Until Stage 7 of `docs/archived/typed-item-params-plan.md` it said nothing about what happens when a caller sends a field the kind has no slot for, because the answer was: the value was silently discarded and the request returned success. `points` on an Event, `eventType` on a Task, `complete` on a Simple item — all accepted, all thrown away, with nothing in the response to say so.

**Those requests are now rejected.** The two places where a request's kind is *data* rather than a fact the code knows — `json_api::project_items` (the `itemType` wire field) and `service::import` (the `itemType` CSV column) — share one set of guards in `service::item_input` and fail with the API's ordinary client error naming the field and the kind. Everywhere else in the codebase the typed inputs (`NewTask`/`NewEvent`/`NewSimple`/`NewTemplate` and their `Edit*` counterparts) are built by construction and simply have nowhere to put a wrong field.

Since Stage 8 of that plan that holds the whole way down: `create_project_item`/`update_project_item` and the `items`/`team_items` functions they dispatch to all take `NewItem`/`EditItem` themselves, and `service::item_input::build_item_type` is the single place deciding which of `Schedule`/`Recurrence`/`event_type`/`TeamAssignment` each kind gets to carry. The flat property bags that used to sit between the two — `CreateProjectItemParams` and its five siblings — are gone, along with the ~80 lines of field transcription that copied one into the next.

Two things this deliberately does **not** change:

- **Authority is a separate axis.** A non-admin setting `points` on a perfectly valid Task is still silently preserved-not-applied by `team_items` (see Points). That rule is about *who may*, not about *what fits*, and it keeps its own rationale.
- **A cross-kind boolean carrying `false` is still accepted and ignored.** `complete` is `@required` on `UpdateProjectItem` and on the MCP server's `update_item` tool, so a caller renaming an Event has no way *not* to send it, and `false` discards nothing. `complete: true` on a non-Task is a real request to do the impossible and does fail.

Two rules that used to be enforced by `Item::validate()` also moved to this boundary, unchanged in wording, because the typed inputs make the bad request unconstructable rather than merely invalid: a Task carrying both `parentItemId` and `sourceEventId` (`TaskAnchor` holds one or the other), and a root `itemType: TEMPLATE` (`NewTemplate`'s parent is a non-optional `String`). `validate()` still carries both for every other writer.

On update the wire may omit `itemType`, which means "leave the kind unchanged" — so the handler resolves the kind from the stored item before it can decide which fields are cross-kind. That read is gated behind the membership check rather than merely followed by one: reading first would let a non-member distinguish "this item exists" from "it doesn't" by deliberately sending a bad field and reading which error came back.

**The template trigger:** when `create_item` persists a new Event with `event_type` set, it lists the requester's personal templates, filters for ones whose own `event_type` matches, and calls `copy_template_children_to_event` for each — anchored on the Event's `scheduled_date` (`event_anchor`; an Event structurally has no `due_date` to fall back to). `create_team_item` checks the requester's personal templates *and* the project's own template library; either can match. This fires on **creation only, never update**: creation had no other multi-item side effects to build on, whereas firing on update would need to track whether an item had already fired to avoid re-copying on every edit.

`copy_template_children_to_event` creates exactly **one** new item per matching template: a top-level Task named after the Event and linked to it via `source_event_id` — the only item the Event itself references (an Event structurally can't have children at all). That task's own due date comes from the *template's* own `due_offset_days`, measured off the Event's anchor — the one offset in this codebase allowed to be **positive** (`Item::validate()`'s scoped exception for a root Template, since this task is the Event's downstream counterpart rather than a prerequisite of it; the web UI still defaults the input to `0`, same day as the event). The template's other children then become that task's ordinary `parent_item_id` sub-items via the shared `copy_template_children` (the same function the Templates screen's manual "Use" flow calls directly), each one's own (still non-positive) offset measured off the **parented task's own due date**, not the Event's. That one level of indirection is what makes the plain-edit sync reach the whole subtree: `sync_offset_children` walks by `parent_item_id` (see Recurrence) but has no way to find a `source_event_id`-linked item except through `sync_source_event_tasks`, so folding every template child into the Event's own reference (this trigger's pre-Stage-2 shape) meant only a direct edit to the Event resynced them, never a reschedule of an intermediate parent.

**The new task's assignment** comes from `service::items::resolve_template_assignment`, which reads the root template's own `team_assignment` (see Domain Models/Points): a fixed `assigned_to_user_id` wins outright, otherwise a configured rotation (`ItemRepo::list_template_rotation_members`, a separate table mirroring `item_series_rotation_members` — see Item series' Assignment rotation) picks the next member. `ItemSeries`'s rotation is stateless because its index is pure calendar math off an anchor date and recurrence rule; a template has neither (it fires off ad hoc Event creation), so the index here is instead a plain **count of tasks this template has already produced** — `TaskItem::source_template_id` (stamped only by this trigger and the "Use" flow, never wire-settable, same convention as `series_id`) is what `ItemRepo::list_by_source_template` counts. This is stateless in the same no-repair-needed spirit as series rotation, just counting past firings instead of elapsed calendar cycles — with one accepted gap series rotation doesn't have: two events matching the same rotating template firing near-simultaneously could count the same total and double up on one assignee, judged acceptable for chore-style assignment rather than worth adding locking for. `copy_template_children`'s own per-child copies never carry assignment — only the root's own copy is ever top-level (see `TeamAssignment`'s Domain Models entry).

`item_type` has a service-layer fallback on update (omitting it leaves the kind unchanged, since there's no meaningful "clear" state). `event_type` deliberately has none — it follows the same caller-must-round-trip-to-preserve convention `due_offset_days` and `priority` do, so every update construction site that isn't intentionally clearing it must pass the current value explicitly.

Everything in this section, plus Points below, is implemented in `src/service/items.rs`/`src/service/team_items.rs`. A request reaches them through `src/service/project_items.rs`'s `create_project_item`/`update_project_item`/`delete_project_item`, which dispatch to the personal or team implementation based on whether the request's project has a backing team.

### Scheduled start/end (`scheduled_date`/`scheduled_end_date`)

`Schedule` (see Domain Models) carries `scheduled_date`/`scheduled_end_date` plus their own `has_scheduled_time`/`has_end_time` flags — an optional start→end window independent of `due_date`. Unlike `event_type`, these are purely descriptive ("when do I actually plan to do this") and apply to Tasks as much as Events; they are **not** gated behind kind in the web UI.

They follow `due_date`/`has_due_time`'s exact wiring, not a simplified one: each is a split `<input type="date">` + `<input type="time">` pair rather than one `datetime-local`, plus a companion boolean, because the boolean disambiguates "the user typed a time" from "only a date was given and a time got synthesized" — without it the UI can't correctly hide the time portion on redisplay. The one deliberate difference from `due_date`: each screen's `combine_local_to_utc` takes the synthetic fallback time as a parameter, because a window's *start* defaulting to end-of-day would be backwards. `scheduled_date` defaults a bare date to **start**-of-day; `scheduled_end_date` (like `due_date`) to **end**-of-day, matching how calendar apps treat all-day ranges.

Like `due_date`, all of these are set by **direct overwrite** on create/update — no service-layer merge — so every call site that round-trips `due_date` must round-trip these four too. `create_item`/`update_item` (and their team counterparts) reject `scheduled_end_date < scheduled_date`; that check lives in `src/service/items.rs` rather than `Item::validate()`, since it postdates the split and never needed to be a domain-level rule.

**Deferred, not implemented:** whether `scheduled_date` should become the *primary* date for tasks (Todoist's model) was raised mid-development and left open. Item series materialization is already `scheduled_date`-primary, which is the closest thing that has landed. The calendar's preset grouping, `list_due`/`prl items due`, and web-UI field prominence on plain items remain `due_date`-only.

**Known design tension, deliberately left as-is.** Every bare (no-time) date anywhere in this app — `combine_local_to_utc` in the web UI, `parse_csv_date` in the importer, the iCal sync's all-day handling — is anchored to a real UTC *instant* computed from the submitter's timezone at submission time (end-of-day for `due_date`/`scheduled_end_date`, start-of-day for `scheduled_date`). The stored value is therefore frozen to whichever zone was in effect then, not floating with the viewer: submit a bare due date from London, view it from New York, and it can display as the previous calendar day. A "floating calendar date" model — where a date with `has_due_time == false` redisplays as the same calendar day regardless of viewer, collapsing to a real instant only once a time is attached — would be the more intuitive fix, and `has_due_time` is already the right hook for it, but it means changing date *display* everywhere the app shows a date (web UI, CLI `fmt_date`, MCP responses). Explicitly judged not worth the complexity for now; a noted gap, not a bug to silently work around.

### Per-team roles & admin bootstrap (`src/domain/team.rs`, `src/service/teams.rs`, `src/service/projects.rs`)

**Team-management authority and item/points authority are two different things**, both per-team-or-per-project rather than global (there is no `users.role`).

- `team_members.role` (`TeamRole`, `Admin`/`Member` — a real enum with `as_str`/`FromStr`/`Display`, following `ItemType`'s precedent, not a raw string) gates **team-management** actions only: inviting, renaming, `set_team_member_role`, via `require_team_admin`. A team's creator becomes its first admin automatically, and the last remaining admin can't be demoted.
- `project_members.role` gates **item and points authority** (who may set `points`/`assignedToUserId`), via `require_project_admin`/`is_project_admin`. This moved off `team_members.role` in Stage C1 of `docs/archived/project-abstraction-plan.md` specifically so a personal project — which has no team at all — can be gated the same way a team-backed one is. It's seeded for a project's owner at creation and kept in sync with an attached team's membership by `attach_team_to_project`.

The two can genuinely disagree: a team admin is not automatically a project admin unless that sync has run. `team_members` has no `points` column — that was dropped in Stage C4 once nothing read it. The one bootstrap exception lives in the auth middleware (see Auth).

### Points & the activity log (`src/service/team_items.rs`, `src/service/activity_log.rs`)

Points live in `TeamAssignment` inside `TaskItem` (see Domain Models) and exist **only on team-backed-project items**, top-level only, settable only by that project's admin — `create_team_item`/`update_team_item` silently strip a non-admin's attempted value rather than rejecting the whole request. That silent strip is about *authority* and survives Stage 7 of `docs/archived/typed-item-params-plan.md` untouched; sending `points` on a non-Task is a different thing entirely and is now rejected at the boundary (see Cross-kind fields at the boundary). Completing a points-bearing top-level team item awards its points to `assigned_to_user_id` — **never to whoever clicked complete** — via `ProjectRepo::add_project_points`. A root `TemplateItem`'s own `team_assignment` (see Events) follows the identical team-backed/admin-gated-points rules, resolved by `service::templates::resolve_template_assignment_input` — but it's a spec carried onto a future task at instantiation time, not a live points-bearing item itself, so none of this section's completion/award mechanics apply to the template row.

**Completion is not assignment-gated:** any project member may complete any team item, assigned to them or not. Points still only ever go to the assignee, so an unassigned item's completion has no one to award and produces no activity-log entry at all.

**Logging is broader than points-awarding.** Every top-level completion — team or personal, points-bearing or not — writes an `activity_log` row; only the *award* is points-gated. Un-completing reverses the award (or the points-less entry) by looking up the most recent unreversed entry for that item+user.

An item series carries its own `assigned_to_user_id`/`points` mirroring `TeamAssignment` one level up (see Item series), and `get_or_materialize_occurrence` copies both onto every occurrence it materializes — so a materialized occurrence's completion awards points exactly like any other team item. There is no series-level points bookkeeping.

The activity feed's manual **Undo** is a separate action on the log entry itself, not the item. It predates the recurrence retirement, when a recurring item's completion deleted the row and left nothing to un-complete in place. That case no longer exists, so undo now **also reopens the item**: `reverse_and_reopen` pre-checks `item_series::validate_uncompletable`, *then* reverses the points, then delegates into `update_project_item`'s own `complete: false` path — the exact path the checkbox uses, so the series cursor restore and every completion guard apply identically regardless of which UI triggered it. There is exactly one "uncomplete an item" implementation, not two that can drift. The pre-check must run *before* the reversal: `reverse_entry` has no undo of its own, so rejecting at the reopen step would leave points clawed back and the entry marked reversed for an occurrence that still failed to reopen.

Both reversal paths share one `reverse_entry` and coordinate through a `reversed` flag; `mark_reversed`'s `WHERE reversed = 0` guard is the only atomic claim either has, so whichever gets there first wins and the other silently no-ops (and the reopen is itself a no-op on an already-incomplete item). `activity_log` rows carry a nullable `team_id` (`None` for a personal item) and a nullable `project_id`. `team_id` predates the Project abstraction and stays live because the legacy `ListTeamActivityLog`/`UndoActivityLogEntry` operations were never retired and still read it; `project_id` is what every other read keys off. The table is completion-events-only, append-only, no retention policy — reversal flips a flag, never deletes.

### Priority (`src/domain/item.rs`, `src/domain/item_series.rs`)

`priority: Option<i32>` (1 = highest, 4 = lowest, `None` = unset/lowest) exists on Task items and Task series. **Deliberately not a sort key** — it briefly was, and was reverted the same day. Every list stays due-date-ordered, undated last, exactly as before priority existed. It is **filterable** instead: `ListFilters::priority` (`All | Exact(1..=4)`), applied both to real items and to still-virtual/skipped series occurrences, round-tripped through the query string like every other filter dimension.

Deliberately **not** modeled like `points`/`assigned_to_user_id` despite the structural resemblance (a Task-only field): it's a plain personal-productivity field carrying none of `TeamAssignment`'s restrictions — settable on a personal or team-backed project, on a child as well as a top-level item, by any project member, never admin-gated. So it sits as its own field on `TaskItem` rather than inside `TeamAssignment` or the shared `Recurrence`/`Schedule`. `ItemSeries::priority` mirrors `points` structurally but `validate_series_priority` checks only Task-kind and the 1–4 range — no team or admin requirement. A materialized occurrence inherits the series' priority, and a still-virtual one carries it too, so filtering ranks unmaterialized occurrences correctly.

`priority` follows `event_type`'s direct-overwrite convention on update, and is part of `is_pure_complete_toggle`'s allowlist (see Completion-transition guards), so a completed item's priority can't change without un-completing first. `copy_template_children` carries it onto each copy, like `due_offset_days`.

### Completion-transition guards

**Three rules gate completing an item**, deliberately living in different layers:

1. **Incomplete direct child** — `has_incomplete_children` (`src/service/items.rs`/`team_items.rs`), for both personal and team items. Direct children only is sufficient by induction: each child was gated the same way when it was completed.
2. **Incomplete dependency** — checked in `project_items::update_project_item` (see Item dependencies), one layer up from the others because dependencies are never threaded into `items::update_item`/`team_items::update_team_item`. Only on a genuine incomplete→complete transition, not a no-op re-completion or a plain field edit.
3. **Outstanding series sub-item** — see Item series & sub-items.

Separately: once `complete == true`, editing any field but `complete` is rejected (`is_pure_complete_toggle`, an explicit field allowlist rather than a derived `PartialEq`, because a freshly-built `Item` spuriously differs from `current` on defaulted fields like the query-computed `has_children`). The only way to edit a completed item is to un-complete it first; the web UI hides each read-only detail view's Edit link when complete. Template children are exempt — they have no completion concept.

### Item dependencies (`src/service/item_dependencies.rs`)

"Depends on" is deliberately narrow: **Task-only, and siblings only** — same project, same `parent_item_id` (two top-level items count as siblings). That scope is what keeps the completion guard a same-project lookup with no cross-project permission check of its own, and keeps the picker a list of already-loaded siblings rather than a project-wide search. Self-dependency is rejected, and `validate_dependency_graph` walks the reachable subgraph to reject cycles. Clearing is always allowed regardless of kind — it's the only way rows on an item whose `itemType` has since changed could ever be removed.

A write replaces the whole set, called from `update_project_item` *after* the item's own fields persist, mirroring `sync_item_reminders`' post-update side-effect shape. `None` means "leave dependencies alone", following the omission convention. The completion guard itself is rule 2 in Completion-transition guards above.

### Reminders, notifications & push (`src/domain/reminder.rs`, `src/service/reminders.rs`, `src/service/push.rs`, `src/push.rs`, `src/web_ui/notifications.rs`)

A `Reminder` is one "notify `user_id` at `remind_at`" row, one per (item, `ReminderKind`) — `Due`/`ScheduledStart`/`ScheduledEnd`, a real closed enum (following `TeamRole`, not `event_type`'s open-string precedent, because it's a small fixed set with real match-arm behavior on both sides).

Reminders are **derived, never authored**. `sync_item_reminders` recomputes an item's whole set from its current state after every create/update in the `project_items` funnel, and clears them on delete — always a full delete-then-reinsert resync rather than a diff, which is cheap and correct regardless of which field changed (the same "just recompute" choice `sync_offset_children` makes). Current scope fires at the date itself: no user-configurable offset, no mutation UI. Recipient resolution mirrors Points — a personal project's owner, or a team-backed item's assignee — and an unassigned team item gets its rows cleared rather than fanning out to the whole project. Task/Event only (Simple has no dates; a Template is a blueprint, not a commitment), and a completed item's rows are cleared rather than left to go stale; un-completing recomputes them.

A reminder carries **two independent delivery markers**, deliberately: `sent_at` is the in-app dismiss marker, `push_sent_at` the push channel's. Dismissing in-app must not retroactively suppress a push that already fired, and vice versa; the only coupling is that the push sweep skips anything already dismissed in-app. `source` is an open string, always `"AUTO"` today — a future custom-reminder UI adds `"CUSTOM"` rows with no schema change. In-app notifications (`src/web_ui/notifications.rs`) render these same rows as a badge, a list, and a dismiss action; there is no separate notifications table.

**Push is optional and silently absent when unconfigured.** `PushConfig::from_env()` needs `TODO_VAPID_PRIVATE_KEY`/`TODO_VAPID_SUBJECT`; without them `main.rs` logs "push notifications disabled" and never spawns the sweep. A `PushSubscription` stores a browser's endpoint plus the *subscriber's* `p256dh_key`/`auth_key` — distinct from this server's VAPID keypair, which identifies the server to the push service rather than encrypting to a subscriber. The 60-second sweep delivers due reminders and prunes subscriptions the push service reports `Gone`.

`service::push` holds **the codebase's one deliberate global**, a `OnceLock<PushRuntime>` set at startup. Push also fires on events (`notify_completion_change`, `notify_assignment`, `notify_comment`) from deep inside service functions reached from ~30 handler call sites; threading config plus two repos through every one of them, purely for a best-effort fire-and-forget side effect, would touch every call site for no behavioral gain. Every notification is `tokio::spawn`ed so a push failure can never fail or add latency to the request that triggered it. Note the completion notification fires at **any** nesting depth, unlike points and activity-log rows, which are top-level-only.

### Attachments & comments (`src/service/comments.rs`, `src/service/attachments.rs`, `src/storage/attachment_store.rs`)

Both are **Task-only and open to any project member** — no admin gate. Creating and deleting an attachment is open to any member; **editing or deleting a comment is author-only**. Comments on a virtual series occurrence are impossible by construction: a virtual occurrence has no `items` row to attach one to.

**An attachment always belongs to a comment**, never to an item directly — that's what lets a file be annotated by the comment's own text. The web UI's real creation path is `create_comment_with_attachment`, where `body` may be empty *if* a file is present (the file is the content, the text an optional caption); the plain `create_comment` that the JSON API/CLI/MCP path calls has no upload concept and still requires non-empty text. `Attachment` denormalizes `item_id`/`project_id` alongside `comment_id` (as `Comment` does relative to `Item`) so an ownership check never joins through `comments`, and download/delete verify the attachment against the URL's project and item rather than trusting the id alone — a guessed or leaked id can't read bytes out from under an unrelated project.

**Metadata and bytes are stored separately on purpose.** `AttachmentRepo` holds filename/size/`storage_key`; `AttachmentStore` holds the bytes under an opaque `storage_key` only the store implementation interprets. That seam is what makes the blob backend swappable (an S3-compatible store later) without touching the repo, the service, or any handler. `LocalFsAttachmentStore` writes under `TODO_ATTACHMENTS_DIR` (default `./attachments`) and is deliberately unaware of whether that path is local disk or a network mount — a self-hoster points it at an SMB/NFS mount and no code path changes (`docs/synology-attachments-mount.md`).

Two accepted rough edges. The size cap (`MAX_ATTACHMENT_SIZE_BYTES`, 25MB) is enforced **twice** — in the service and as axum's `DefaultBodyLimit` on the `/web/*` router, which must stay above it plus multipart overhead or a large-but-valid upload is rejected before ever reaching the real check. And the two writes aren't transactional in either direction: upload writes bytes then metadata, delete removes metadata then bytes, so a failure between them orphans a blob rather than leaving a metadata row pointing at bytes that don't exist. Nothing reaps orphans today.

### Calendar subscriptions & iCal import (`src/service/calendar_subscriptions.rs`, `src/service/calendar_sync.rs`)

A `CalendarSubscription` is one project admin's subscription to an external (Google Calendar) iCal feed (`docs/archived/google-calendar-import-plan.md`). Creating one is admin-only and syncs immediately, so events appear without waiting up to 15 minutes for the background sweep; a sync failure never fails the creation — it's recorded on the row as `last_sync_error` for the UI to surface, and a failed fetch never clears already-imported items.

`calendar_sync` **writes through `ItemRepo` directly rather than through `service::project_items`**, deliberately: that funnel enforces per-request membership and role checks that don't apply to a background process, and its read-only guard would reject the sync's own writes to already-imported items. Imported items are Event-typed and carry `google_event_id` (the iCal `UID`) and `calendar_subscription_id` — the keys the diff runs on, and the reason those two fields sit on `EventItem` (see Domain Models).

Two subtleties worth knowing before touching it:

- **All-day values have no timezone**, and a background sync has no request-scoped viewer to borrow an offset from (unlike a manually created all-day item, whose creator's browser bakes one in). The sync resolves the *subscription creator's* `User::timezone`, falling back to UTC, and localizes all-day dates against it — fixing all-day events that displayed a day early for any viewer behind UTC. A different viewer's zone can still disagree, but that's the same already-accepted limitation described under Scheduled start/end, not a new gap.
- **Recurring masters are expanded**, one synthetic pseudo-event per occurrence, inside a tight sliding window, each with a deterministic `"{uid}::{occurrence_start}"` id derived from its unmodified RRULE-computed timestamp — so the existing `google_event_id`-keyed diff handles create/update/delete for them with no changes of its own. `RECURRENCE-ID` override events are matched to their slot by that same original timestamp and swapped in before the diff runs; a cancelled override drops its slot exactly like an `EXDATE`.

### CSV import & the import template (`src/service/import.rs`)

`ImportProjectItems` and `GetItemImportTemplate` are deliberately **CLI/MCP-only — no web UI screen**. `GetItemImportTemplate` is the one operation outside `/users`/`/teams`/`/projects`, so it needed its own `/items` route registration in both auth-mode branches of `api_router`.

**The server, not the caller, parses the raw CSV** (`csv: String` on the input). That centralizes all parsing, validation, and creation in `import_project_items`, which reuses `create_project_item`'s existing dispatch and validation with zero duplication — every rule described elsewhere in this file applies per row for free. `prl` and the MCP server just pass a file's text through; neither needed a CSV dependency.

**Best-effort, not transactional:** each row is attempted via its own `create_project_item`; valid rows are created and invalid ones collect into a per-row result rather than aborting the import. That per-row channel is also how a cross-kind column is reported (see Cross-kind fields at the boundary): a `points` value on an `EVENT` row fails *that row* and the rest of the file still imports. A blank cell reads as absent, so a mixed-kind file whose fixed column set is only populated where it applies is unaffected — which is what makes rejecting workable for a columnar format at all. Row numbers count the header as row 1. Column mapping is header-driven and order-independent — extra or missing optional columns are simply never looked up. `parentItemId` may be given but must reference an item that already exists, not another row in the same file; there's no intra-file parent/child resolution.

`format` is a plain unenforced string defaulting to `"PRL"`, with a single match as the seam for a future format. `PRL` is this app's native, lossless format: headers match the API's own JSON field names exactly, dates use the same `YYYY-MM-DD`-or-Unix-timestamp convention the CLI flags do. There is deliberately **no `recurrence` column** — a row carrying one is a hard error for that row rather than a silent drop, because bulk import is for loading a batch of items, not authoring a recurring series (create a series instead, see Item series). A `"TODOIST"` format was explored and **not** implemented: its export needs a natural-language date parser this app doesn't have (`"in 15 days"`), uses `INDENT`-based nesting that conflicts with the flat-only rule, has no machine-readable completion column, and carries several columns with no equivalent here.

A bare (no-time) date in the CSV is interpreted in the *caller's* local time via a `timezoneOffsetMinutes` request field, mirroring the web UI's own conversion — `prl` computes it from the local machine, the MCP server defaults to its host's offset. This was a real bug fix: without it, a bare date near midnight landed on the wrong calendar day once viewed back in local time. The residual instant-vs-floating-date limitation is the one described under Scheduled start/end.

`GetItemImportTemplate` returns a static 3-row constant — one Task, one Event, one Simple, deliberately no Template row, since a root `itemType: TEMPLATE` is rejected on this path like every other (a row naming an **already-existing** Template as its `parentItemId` is the one way through, per the template-child exception in the Events section — there is no intra-file parent resolution, so a file cannot create a template and then nest under it).

### Web UI (`src/web_ui/` + `templates/`)

Server-rendered Askama + htmx; no browser-side SPA or generated TS client. `templates/base.html` is the one root document; `hx-boost="true"` with `hx-target="#page"`/`hx-select="#page"` on `<body>` keeps the header and scripts stable across boosted navigation while `#page` swaps. Mutations that shouldn't touch the rest of the page scope their own narrower target instead of inheriting the body-level one.

`src/service/` holds the business logic both `src/json_api/` and `src/web_ui/` call, so the two presentation layers stay thin wrappers rather than duplicating rules. `ItemError` (`src/service/error.rs`) is presentation-agnostic — no HTTP or HTML knowledge; `src/web_ui/error.rs` adds the `IntoResponse` impl that renders it. **Preserve that split** in any error-handling change.

**The row-editing convention**, followed by every dedicated screen: no inline click-to-edit and no edit-form-on-click. A row's name is a boosted link to that item's **read-only** detail page, which has its own Edit link to a sibling `/edit` route holding the actual form. The form still PUTs back to the non-`/edit` resource URL with its target scoped to the item's own wrapper id. Because the read-only view also carries a complete-toggle identical to the row's, and all three post to the same endpoint, each screen's update handler renders **three fragments concatenated into one response** (row + fields + view), each caller's `hx-select` plucking out its own. Template children are the one variant without the toggle — no completion concept — so their handler stays a two-fragment response.

**Screens are project-scoped, not personal/team-scoped.** The original per-item-type-times-personal/team split was collapsed once every screen was rebuilt on `ProjectItem`: a personal item just lives on a project with no backing team, so one screen per item type serves both, dispatching on `project.team_id` internally (whether to show an assignee dropdown or points field) rather than living at a different URL. `nav.rs`'s `ActiveContext` is `Project(String) | AllProjects | None` — there is no persisted "active project", it's always derived from the URL.

Run `ls src/web_ui/` for the screen list; the non-obvious parts are:

- **The default landing page is `/web/tasks`** (`all_projects_tasks.rs`), the cross-project Tasks list — `GET /` and the header logo both redirect there. `all_projects_events.rs` and `main_calendar.rs` are its siblings under `ActiveContext::AllProjects`.
- **Cross-project screens apply a filter the per-project ones have no equivalent of**: Events always show, but Tasks show unrestricted only on a personal project and only when assigned to the requester on a team-backed one — otherwise every teammate's tasks would show, defeating the "what's mine, across everything" purpose. Each screen duplicates that predicate locally rather than sharing it, per this codebase's per-screen-helper precedent.
- **`project_activity.rs` reads `activity_log.project_id`, not `team_id`** (see Points).
- Legacy `/web/dashboard*` paths survive only as redirects to the renamed Calendar routes — cheap insurance against stale bookmarks.

The desktop sidebar is a fixed-position overlay that slides via `transform: translateX(-100%)`, a compositor-only property, so toggling it can never reflow `#page` — verified once with a live check that `#page`'s bounding box is byte-identical before, during, and after. The deliberate tradeoff: at narrower widths the expanded sidebar overlaps content rather than pushing it aside. State is `localStorage`-only, read synchronously in `<head>` before `<body>` renders so a fresh load never flashes the wrong state, and collapsing also sets `visibility: hidden` — without it the links stay in tab order despite being off-screen.

The timezone offset is sent as an **`X-Tz-Offset-Minutes` header**, not a form or query parameter: as a parameter it leaked into `hx-push-url`'d URLs and broke `hx-select="#page"` navigation. A `tz_offset` cookie is the fallback for non-htmx requests.

Tailwind Plus component restyling: see `.claude/skills/tailwind-plus-restyle/SKILL.md`. CLI: `todo-cli/CLAUDE.md`. MCP server: `mcp-server/CLAUDE.md`.

## Key Workflows

**Adding/changing a Smithy operation:**

1. Edit the `.smithy` file
2. `task codegen`
3. Fix Rust compile errors (the generated types changed)
4. Add/update the handler and wire it into `PeoplesRepublicOfLists::builder(...)`

See the touch-point checklist below for every file that may need updating.

**Adding a DB column:**

1. Add it to `CREATE TABLE IF NOT EXISTS` in `create_pool()` — this is what makes a fresh DB correct without ever running the migration
2. Add a file under `src/storage/migrations/` implementing `Migration` with the next version, guard each `ALTER TABLE ... ADD COLUMN` with `column_exists()`, and register it in `all_migrations()`
3. Update the affected SELECT/INSERT/UPDATE queries and row mapping

**Web UI-only change:** edit `templates/*.html` → `cargo build` (Askama embeds templates at compile time, so a Rust rebuild is required even for template-only edits). If Tailwind classes changed, also run `task web-styles`.

**Switching auth modes:** `TODO_AUTH_MODE=caddy` trusts caddy-security headers; `internal` (or unset) uses the built-in OAuth flow. For local dev in caddy mode without Caddy, set `TODO_DEV_EMAIL`.

## Touch-Point Checklist

Everything that must be updated when the Smithy model changes. The generated crates (`todo-server-sdk/`, `todo-client/`, `todo-typescript-client/`) update themselves via `task codegen`; everything else is hand-written.

### Adding or removing an operation

| File | What to do |
|------|-----------|
| `model/src/main/smithy/*.smithy` | Add/remove the operation definition |
| *(run `task codegen`)* | Regenerates the Rust SDKs + TS client |
| `src/main.rs` | Add/remove the handler wiring in `PeoplesRepublicOfLists::builder(...)` |
| `src/json_api/mod.rs` / `src/web_ui/mod.rs` | `pub mod <module>;` if you added a handler file |
| `src/service/*.rs` | The shared business-logic function, if applicable |
| `src/web_ui/**` + `templates/**` | The screen/route, wired in `build_web_router()` |
| `mcp-server/src/index.ts` | Tool definition in the list + `case` in the switch |
| *(run `cd mcp-server && npm run build`)* | Changes aren't live until this runs |
| `todo-cli/src/*.rs` | Subcommand variant and match arm |
| `docs/prl-user-guide.md` | Document or remove the command |
| **`CLAUDE.md`** | **Only if the change alters a stated invariant or adds a feature area — see below** |

### Updating this file

Update the section that **owns** the fact you changed; don't restate it elsewhere. Concretely, a change needs a CLAUDE.md edit when it:

- **adds a feature area** (a new domain concept with its own service module) — that gets a new `###` section explaining why it's shaped that way, not what files it has;
- **changes an invariant or a rule** stated here (what gates completion, who may set a field, what's immutable after creation, which layer owns a check);
- **reverses or supersedes a decision** recorded here — say what replaced it and why, since the rejected alternative is often the most valuable thing on the page;
- **moves a field between types** — then grep this file for the field name and fix *every* section that names it, not just the one you were reading.

It does **not** need an edit when you add a file, a repo trait, a screen, or a route that follows an existing pattern. Those are inventory; `ls` and the router are the source of truth, and listing them here only creates something to go stale. Several code comments point at named sections here (`root CLAUDE.md's Attachments section`), so keep `###` headings stable — rename one and you orphan those references.
