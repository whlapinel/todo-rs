# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Working style

Do not use sub-agents (the `Agent` tool, including `Explore`/`general-purpose`/etc.) for work in this repo — do research and implementation directly. This applies even for "just research, no edits" tasks like surveying existing patterns before implementing a feature.

## Git

Do not add `Co-Authored-By` trailers to commits.

Before creating any commit, run plain `cargo fmt` (no path arguments) from the repo root, then stage any resulting formatting changes as part of the commit. Keeping the whole repo uniformly formatted this way means there's never a partially-formatted file left for a later scoped `rustfmt <file>` or `cargo fmt -- <file>` invocation to collide with — which is what caused repeated formatting breakage in the past (a scoped invocation on a crate-root file like `src/main.rs` reformats every file transitively reachable through `mod` declarations, producing a huge unrelated diff). Always use plain `cargo fmt` with no arguments; never invoke the `rustfmt` binary directly or pass specific files to `cargo fmt --`.

## Commands

See `Taskfile.yml` for the full task list (`codegen`, `run`, `build`, `check`, `web-styles`, `cli-build`, `cli-install`) plus `cargo test` for the Rust test suite.

Live-server smoke test (requires `TODO_API_URL` + `TODO_API_TOKEN`):


For UI-only changes (no Smithy or Rust changes): edit `templates/*.html`, then `cargo build` picks it up (Askama embeds templates at compile time). If Tailwind classes changed, also run `task web-styles`.

**Don't use Playwright (or any other browser-automation tool) to click-through/verify UI changes** — the user does that verification themselves; it burns tokens for no benefit here. Verify with `cargo build`/`cargo test`/`task check` and a careful read of the template/handler diff instead, and say so explicitly if live-in-browser behavior can't actually be confirmed that way.

Formatting policy (never invoke `rustfmt` directly or scope `cargo fmt` to specific files) is covered in the Git section above.

`task codegen` requires JDK 11+. It compiles the smithy-rs Kotlin codegen from source via a Gradle composite build — first run takes several minutes, subsequent runs are cached in `~/.gradle/caches/`.

## Architecture

### Full Pipeline

```text
model/src/main/smithy/*.smithy
        │  (task codegen / ./gradlew :model:assemble)
        ▼
todo-server-sdk/          ← generated Rust crate (DO NOT EDIT)
todo-client/              ← generated Rust client crate (DO NOT EDIT)
todo-typescript-client/   ← generated TS client (DO NOT EDIT) — codegen output only, no consumer
        │
        ▼
src/main.rs                    ← handler implementations, axum server wiring
src/json_api/                  ← JSON API handlers backing the Smithy service
src/web_ui/ + templates/       ← server-rendered UI (Askama + htmx)
todo-cli/src/client.rs         ← prl CLI (standalone crate, uses generated todo-client)
```

There is no browser-side TypeScript client or SPA — the UI is server-rendered (see the Web UI section below). `todo-typescript-client/` is still generated by `task codegen` (nothing currently reads it) but nothing in this repo builds or consumes it.

### Smithy Model → Generated Code

The `.smithy` files in `model/src/main/smithy/` define the full API contract. `User` is the only Smithy `resource`; every item is owned by exactly one **`ProjectItem`** — identifiers `{projectId, itemId}`, at `/projects/{projectId}/items/{itemId}` (`model/src/main/smithy/project_item.smithy`). This replaced the original `User → Item` (personal, `/users/{userId}/items/{itemId}`) and `TeamItem` (team-scoped, `/teams/{teamId}/items/{itemId}`) resources, retired in Stage C3 of `docs/project-abstraction-plan.md` — every project is either personal (no backing team) or team-backed, so a single project-scoped resource now covers both cases; `assignedToUserId`/`points` still exist on `ProjectItem` but are only meaningful on a team-backed project (see Points section below).

`Team` and `Project` are both plain service operations, not Smithy resources — team CRUD (`CreateTeam`, `GetTeam`, etc.) is scoped under `/users/{userId}/teams`, project CRUD under `/users/{userId}/projects`. The `items` SQLite table carries a nullable `user_id` alongside `project_id` — `user_id` is the pre-Project-abstraction column, kept because `ItemRepo` (see Storage Layer below) still exposes personal-shaped methods alongside the project-shaped ones a `ProjectItem` request actually goes through. `items.team_id` was the team-scoped counterpart to `user_id`; it was dropped entirely in Stage 6 of `docs/team-id-removal-plan.md` once `project_id` became the sole scoping key for team-backed items too. Items support nesting via `parentItemId`.

smithy-rs (a Gradle composite build via the `smithy-rs/` git submodule) generates:

- `todo_server_sdk::input::*` / `output::*` / `error::*` — typed structs per operation
- `PeoplesRepublicOfLists` — the tower `Service` (HTTP routing + serde handled automatically)
- `PeoplesRepublicOfListsBuilder` — wires async handler functions to operations

Handler signature: `async fn op_name(input: input::OpInput, server::Extension(repo): server::Extension<Arc<dyn Repo>>) -> Result<output::OpOutput, error::OpError>`

The service is also annotated `@httpBearerAuth`. This only affects **client** codegen (generic smithy-rs `codegen-client`, not AWS-specific) — it generates a `Config::builder().bearer_token(Token::new(...))` method and a `BearerAuthScheme` that auto-attaches the `Authorization: Bearer` header on `todo-client`. Server-side codegen (`codegen-server`, → `todo-server-sdk`) has no handling for HTTP auth traits at all — adding/removing this trait never changes generated server code. Actual token verification is, and must remain, hand-written in `src/auth.rs`; the trait only standardizes how the client carries the credential, not how the server validates it.

### Server (`src/main.rs`)

Handlers receive dependencies via `server::Extension` (injected via `tower::ServiceBuilder` layers). The smithy service is nested under `/api`; the server-rendered UI is nested under `/web` (see Web UI section below); `/` redirects to `/web/tasks` (the all-projects Tasks list — see Web UI section below). Compiled CSS/JS for the UI is served from `static/` via axum's `ServeDir` at `/web/static`.

Auth mode is selected at startup via `TODO_AUTH_MODE` (see Auth section below).

### Auth (`src/auth.rs`)

Two modes, selected by the `TODO_AUTH_MODE` env var:

- **`internal`** (default) — full Google OAuth + JWT flow. Requires `TODO_GOOGLE_CLIENT_ID`, `TODO_GOOGLE_CLIENT_SECRET`, `TODO_JWT_SECRET`. Mounts `/auth/google`, `/auth/callback`, `/auth/logout`, `/auth/me`, `/auth/token` routes. The `/auth/token` endpoint issues a long-lived JWT for use by CLI/MCP clients.
- **`caddy`** — also requires `TODO_JWT_SECRET` now (used to verify Bearer tokens, see below). Mounts `/auth/me` and `/auth/token`. `caddy_header_middleware` accepts identity two ways: (1) the `x-token-user-email` header injected by caddy-security for browser sessions — trusted as-is, no signature check, because only caddy-security can set it; or (2) an `Authorization: Bearer <jwt>` header for CLI/MCP requests, verified via `jsonwebtoken::decode` against `TODO_JWT_SECRET` — same check `jwt_auth_middleware` does for `internal` mode. `caddy_auth_token` mints tokens the same way `auth_token` does in `internal` mode, but resolves identity from `x-token-user-email` instead of a session cookie. Set `TODO_DEV_EMAIL=you@example.com` to bypass the header check for local dev without Caddy in front.

  **Cross-repo dependency:** for a Bearer-token request to ever reach path (2) above, the edge reverse proxy must not intercept it first. In production this is caddy-security sitting in front of everything — its `authorize with mypolicy` directive would otherwise 302-redirect *any* unauthenticated request (including ones carrying our own JWT, which caddy-security doesn't recognize) to its login portal before it ever reaches this app. The home-server repo's `Caddyfile.local` gives `todo.lapinel-fam.club` its own dedicated site block with a matcher that skips `authorize` specifically for requests carrying `Authorization: Bearer`, letting them fall through to this middleware instead. See that repo's `CLAUDE.md` for the Caddyfile side of this. If that Caddyfile change is ever reverted, path (2) becomes unreachable in production even though the app code still supports it.

In both modes, `AuthUser { user_id }` is injected into request extensions by the respective middleware and is available to handlers.

**`/web/*` auth and the login page:** `build_web_router()` (in `src/main.rs`) holds every protected `/web/*` route; a separate `build_public_web_router()` holds only `GET /web/login` (`templates/login.html`, "Sign in with Google" linking to `/auth/google`). Only the protected router gets `.layer(middleware::from_fn(auth::web_auth_middleware))` (internal mode) or `caddy_header_middleware` (caddy mode) — the two routers are then `.merge()`d *before* being nested under `/web`, so the login page itself never goes through the auth check that would otherwise redirect it right back to `/auth/google`. `internal` mode's `web_auth_middleware` redirects unauthenticated `/web/*` requests to `/auth/google` (not a bare 401 — see its doc comment in `src/auth.rs`); `caddy` mode's `caddy_header_middleware` still 401s (auth is expected to happen at the edge in production).

### Storage Layer (`src/storage/`)

`sqlite` (`src/storage/sqlite/`) is the sole storage implementation — the `memory`/`dynamo` backends this section used to describe were removed once nothing exercised them. The repo traits themselves (`UserRepo`, `ItemRepo`, `TeamRepo`, `ProjectRepo`, `ActivityLogRepo`, each `#[cfg_attr(test, mockall::automock)]`) live in `src/storage/sqlite/mod.rs`, not a separate top-level `mod.rs`.

`UserRepo` methods include `get_or_create_by_google_id` (used by internal OAuth flow) and `get_or_create_by_email` (used by caddy middleware — looks up by email, creates a record if none exists).

`ItemRepo` carries two method shapes side by side: the original personal-`Item`-shaped methods (`get`, `list`, `create`, `update`, `list_due`, `list_templates`), and the project-shaped unified methods (`get_by_project`, `list_by_project`, `update_by_project`, `list_due_by_project`, `list_templates_by_project`) that every `ProjectItem` request — personal or team-backed — actually goes through. A third, `TeamItem`-shaped set (`get_team_item`, `list_team_items`, `update_team_item`, `list_due_team_items`, `list_team_templates`) existed alongside these until Stage 6 of `docs/team-id-removal-plan.md` removed it, once `src/service/team_items.rs` (which still owns the events/points/completion-guard business logic for team-backed items — see those sections below) finished migrating onto the project-shaped methods and the `items.team_id` column those methods queried was dropped. `src/service/items.rs`/`src/service/team_items.rs` are reached indirectly, via `src/service/project_items.rs`'s two-way dispatch on whether a project has a backing team (see Web UI section below); only the *Smithy-level* HTTP surface for standalone personal/team items is gone from `create_item`/`get`/etc.'s callers, not the underlying service functions themselves.

`ProjectRepo` holds `create`, `get`, `find_personal_project`, `get_by_team`, `update_name`, `attach_team`, `detach_team`, `delete`, `list_for_user`, `list_members`, `member_role`, `set_member_role`, `count_active_admins`, `add_project_points` — this is where role/points authority now lives (see Per-team roles/Points sections below). `TeamRepo` keeps `role`-related methods (`member_role`, `count_active_admins`, `set_member_role`) but no longer has a points method of its own (see Points section below).

SQLite schema management is split in two. The baseline `CREATE TABLE IF NOT EXISTS`/`CREATE INDEX IF NOT EXISTS` statements in `create_pool()` always reflect the *current* full schema, so a fresh DB is correct from the start and never touches the migration system below. Schema changes to already-deployed DBs go through `src/storage/migrations/` — a versioned `Migration` trait (`version()`, `name()`, `async fn up(&self, conn: &mut SqliteConnection)`), one file per migration, run once at startup via `run_migrations(&pool)` (called from `create_pool()`), which tracks applied versions in a `_migrations` table and runs each unapplied migration in its own transaction. Adapted from a sibling project's (`courses-api`) migration system, with one addition: since SQLite's `ALTER TABLE ... ADD COLUMN`/`DROP COLUMN` have no `IF NOT EXISTS` form, every migration guards its `ALTER TABLE`s with `column_exists()` (`PRAGMA table_info`) — necessary because a DB that already has a target column (either a fresh DB whose `CREATE TABLE` already includes it, or an existing DB migrated under the old pre-`_migrations` inline-ALTER-TABLE approach) must not error when the migration runs for the first time.

### Domain Models (`src/domain/`)

Plain Rust structs (`User`, `Item`) — no framework coupling. `Item` stores `deadline` as `Option<DateTime<Utc>>`, `recurrence`/`recurrence_basis` as vestigial `Option<String>` fields (see Recurrence below — item-level recurrence is retired; these two are read-only historical-display leftovers now), and `due_offset_days` as `Option<i32>` (still fully live). `Item.series_id: Option<String>` (added 2026-08-19, Stage A of `docs/unify-virtual-materialized-occurrences-plan.md`) links a materialized item back to the `item_series` it's an occurrence of — set once, at creation, only by `service::item_series::get_or_materialize_occurrence`; no Smithy field, CLI flag, or MCP parameter can ever set or clear it, and it's carried forward unchanged on every update the same way `project_id` is (an item's series membership never changes after creation). `None` for every item not materialized from a series. This is additive to, not a replacement for, the existing reverse lookup `ItemSeriesRepo::find_occurrence_by_item_id` (via the `item_occurrences` table), which several write-path hooks (completion/uncompletion/delete gates in `service::project_items`) still use.

`Item::deadline_from_offset(root_deadline, tz_offset_minutes)` (`src/domain/item.rs`) is the domain-level decision for a child's offset-driven deadline: `due_offset_days.map(|n| end_of_day(root_deadline + n days))`, `None` if no offset is set. Pure and unit-tested in isolation from the handlers that call it. (The item-level `Item::next_recurrence`/`recurrence::next_date` that used to sit alongside this — deciding whether a completed item should spawn a successor — was deleted in Stage 10's retirement; see Recurrence below.)

### Recurrence — retired at the item level (`src/domain/recurrence.rs`)

Item-level recurrence (`Item.recurrence`/`recurrence_basis`, a completed item spawning its own successor via `Item::next_recurrence`) was retired in Stage 10 of `docs/recurring-events-virtual-occurrences-rough-plan.md`: a one-time migration moved every existing recurring item onto an `item_series` (`src/service/item_series.rs`, `src/domain/item_series.rs`, `docs/recurring-events-virtual-occurrences-rough-plan.md` — not yet its own CLAUDE.md section), and the mechanism's code — `Item::next_recurrence`, `clone_children`, `archive_recurrence`, `repoint_source_event_tasks`, and the `recurrence`/`recurrenceBasis` fields on the Smithy `Item`/`ProjectItem` shapes — was deleted. Anyone wanting a recurring item now creates an `item_series` (UI/CLI/MCP), not a single item with a `recurrence` string.

`src/domain/recurrence.rs`'s English-phrase parser (`every N days/weeks/months/years`, `every month on the Nth`, `every [weekday]`) and its `advance_once` stepper are not retired — they're exactly what `item_series`'s own recurrence rule parsing/advancing uses (`src/service/item_series.rs`, `docs/recurring-events-virtual-occurrences-rough-plan.md`). What's gone is only `Item`-level usage of them.

The domain `Recurrence` struct (`src/domain/item.rs`, embedded in `ItemType::Task`/`Event`/`Template`) keeps its `pattern`/`basis: Option<String>` fields and `recurrence_pattern()`/`recurrence_basis()` accessors — deliberately not removed, since they're still read for two legitimate historical-display purposes: a `Template`'s "↻ repeats" badge (an inert copy taken at "Save as template" time, from before this retirement — see `service::templates::create_template`) and any already-completed legacy-recurrence history row that predates the migration. Nothing external can ever populate them again — no Smithy field, no CLI flag, no MCP tool parameter, no web UI form input carries `recurrence`/`recurrenceBasis` anymore, so `create_item`/`update_item`/`create_team_item`/`update_team_item` always construct a fresh item's `Recurrence` as `{pattern: None, basis: None, due_offset_days: ...}`.

**`due_offset_days` is unaffected and stays fully live** — it was never recurrence-specific to begin with (see CLAUDE.md history: this was discovered mid-retirement, not assumed). A child item (`parentItemId` set) or an event-linked task (`sourceEventId` set) still carries `dueOffsetDays: Option<i32>` — days from its top-level item's or linked event's anchor date (negative = before, positive = after) — recomputed via `deadline_from_offset`. `Item::validate()` (2026-08-28) rejects a *positive* value outright (`ItemError::Invalid`, "due offset days cannot be positive") on every write path (`create_item`/`update_item`/`create_team_item`/`update_team_item` all call it) — it never made sense for a sub-item to be due after the thing it supports, and every caller now presents this as "days before due" rather than a raw signed offset: the web UI's offset field (`macros::due_offset_days_field` and every raw `dueOffsetDays` input, `src/web_ui/project_tasks|events|templates/`), `prl items add --days-before-due` (`todo-cli/src/items.rs`, renamed from `--due-offset-days`), and the MCP `create_item`/`update_item` tools' `daysBeforeDue` parameter (`mcp-server/src/index.ts`) all take a non-negative "days before" number and negate it before it reaches the wire/domain layer — `dueOffsetDays` itself keeps its original negative-before/positive-after sign on the wire and in storage, it just can never be written positive anymore. A row written before this check landed may still carry a stale positive value; the check only guards new writes, there's no migration. Two things still drive the offset->due-date recompute:

- `sync_offset_children`/`sync_source_event_tasks` (`src/service/items.rs`) — fire on **any plain edit** that moves a top-level item's or Event's own anchor date (`item_anchor`, `due_date.or(scheduled_date)`), independent of recurrence entirely. This is what keeps a template-auto-triggered Event's children (see Events below) tracking their parent when it's rescheduled. `update_item`/`update_team_item` call these unconditionally after persisting a non-recurring update; children are updated **in place** (same id), and a child with no `due_offset_days` is **left untouched** rather than cleared — it isn't derived from the parent, so a parent edit shouldn't touch it.
- `copy_template_children`/`copy_children_as_template` (`src/service/items.rs`) — the Templates screen's "Use" flow and the event-trigger mechanism (see Events below), and now also `item_series`'s own materialization when a series has a `template_item_id` linked (`src/service/item_series.rs`, `docs/recurring-events-virtual-occurrences-rough-plan.md`).

Everything in this section, Events below, and Points below lives in `src/service/items.rs`/`src/service/team_items.rs`. An HTTP request reaches them via `src/service/project_items.rs`'s `create_project_item`/`update_project_item`/`delete_project_item`, which dispatch to the personal (`items.rs`) or team (`team_items.rs`) implementation based on whether the request's project has a backing team (`Project::team_id`) — see Web UI section below for how the web UI itself calls in.

### Events and template triggers (`src/domain/item.rs`, `src/service/items.rs`, `src/service/team_items.rs`)

`Item::item_type: ItemType` (`Task` / `Event` / `Template`) classifies what kind of row an item is — it replaced a separate `is_template: bool` plus what would have been an independent `is_event: bool`; those were both answering "what kind of thing is this row," so they're one field instead of two that could drift out of sync. `Task` is the default; `Event` is the same struct, just `scheduled_date`-primary for display rather than `due_date`-primary; `Template` is a template-library artifact (`src/service/templates.rs`'s `create_template` is the only place allowed to set it — `create_item`/`update_item`/`create_team_item`/`update_team_item` reject `itemType: TEMPLATE` via `ItemError::Invalid`).

`ItemType` is this model's one genuine Smithy `enum` shape (`TASK` / `EVENT` / `TEMPLATE`) — every other finite-valued field (`eventType`, for instance) is a plain `String` compared by literal at the Rust layer, with no Smithy-level validation. `ItemType` is the deliberate exception: smithy-rs generates a real closed enum server-side (`todo_server_sdk::model::ItemType`, `TryFrom<&str>` rejecting unrecognized strings with a `ConstraintViolation` at the deserialization boundary — invalid values never reach handler code at all) and an open one client-side (`todo_client`/`todo-cli`, with a deprecated `Unknown` catch-all variant for forward compatibility). `src/json_api/mod.rs`'s `to_domain_item_type`/`to_sdk_item_type` convert between the generated enum and the hand-written domain one at the json_api boundary.

`Item::event_type: Option<String>` is a plain, unvalidated-by-Smithy string (matching `recurrence`'s precedent — no Smithy-level enum) with a dual meaning depending on what it's set on:

- On an `Event`-typed item, it's "this occurrence's category" (e.g. `"rain"`).
- On a `Template`-typed item, it's "fire me when a matching item is created."

`Item::validate()` (`src/domain/item.rs`) restricts `event_type` to these two types — `Some(..)` is rejected unless `item_type` is `Event` or `Template` (the `Template` allowance exists even though `create_template`'s path never actually calls `validate()` today, so the check stays correct if that ever changes). `project_tasks/`/`project_simple_lists/` have no `event_type` form field at all, personal-project or team-backed — only `project_events/` and the templates screens expose it. This was tightened from an earlier, unrestricted version where every dedicated screen exposed the field regardless of type; `prl items add`/`update_item`/`update_team_item` and the MCP server's `create_item`/`update_item`/`create_team_item`/`update_team_item` tools still accept `eventType` as a plain parameter with no client-side type check beyond `prl`'s own (see CLI section below) — the server is the actual enforcement point for everything else.

When `create_item` persists a new item with `event_type` set, it calls `repo.list_templates(user_id)` (personal templates only), filters for templates whose own `event_type` matches, and for each match calls `copy_template_children` (`src/service/items.rs`, the same function the templates screen's "Use" flow already calls) to copy that template's children onto the new item — anchored on `item_anchor(&item)` (`due_date.or(scheduled_date)`). `create_team_item` does the analogous check against both `repo.list_templates(requester_user_id)` (the requester's personal templates) and `repo.list_templates_by_project(project_id)` (the project's own template library — see the team-backed-project case of `project_templates/` below) — either can trigger a match. This only fires on **creation**, not update: `create_item`/`create_team_item` had no other multi-item side effects to build on, whereas firing on update would need to track whether a given item already fired its trigger to avoid re-copying on every edit. Since `event_type` is now Event-only for real items, this trigger effectively only fires when creating an `Event` (Templates never reach `create_item`/`create_team_item` — they're created via a separate path, see above).

The copied children are deliberately parented **under the event itself** (not, say, kept as siblings linked by some other id) — the reason is exactly what makes the plain-edit sync described in Recurrence above work for them: `update_item`/`update_team_item`'s `sync_offset_children` walks by `parent_item_id`, so an auto-triggered template child (which carries whatever `due_offset_days` its template-child original had) tracks the event's date on any reschedule, not just when the event recurs. Task children under an `Event` parent aren't a special case or a type-safety compromise — it's the same structure Events' own manually-added sub-items already use (see Screens below), so nothing about the auto-trigger's parenting choice is inconsistent with the rest of the model.

`item_type` has a service-layer fallback on update (`params.item_type.unwrap_or(current.item_type)` — omitting it from an update leaves the item's kind unchanged, since there's no meaningful "clear" state for a field that always has a concrete default). `event_type` has no such fallback (`item.event_type = params.event_type.clone()`, a direct overwrite) — it follows the same caller-must-round-trip-to-preserve convention `due_offset_days` already does, so every `UpdateItemParams`/`UpdateTeamItemParams` construction site that isn't intentionally clearing `event_type` must pass `current.event_type.clone()` explicitly (`todo-cli`'s `prl items done` does this for `due_offset_days` already — see CLI section below — and does the same for `item_type`/`event_type`).

### Scheduled start/end (`scheduled_date`/`scheduled_end_date`)

`Item` also carries `scheduled_date`/`scheduled_end_date: Option<DateTime<Utc>>` and their own `has_scheduled_time`/`has_end_time: bool` flags — an optional start→end window, independent of `due_date`. Unlike `event_type` (a trigger key), these are purely descriptive — "when do I actually plan to do this" — and apply to `Task` items just as much as `Event` items; they are **not** gated behind `item_type == Event` in the web UI. `deadline_from_offset`/`copy_template_children` are basis-agnostic plain-parameter functions; a child's own recomputed date is always written to *its* `due_date`. `copy_template_children`'s own anchor (`item.due_date.or(item.scheduled_date)`, used for template-trigger copies at creation, and now also for `item_series` materialization when a series has a `template_item_id` linked — `src/service/item_series.rs`) is a plain fallback with no recurrence-basis concept to be tied to (item-level recurrence basis is retired — see Recurrence above; `item_series`'s own `basis` field, gap 1, is the current analogous mechanism — `COMPLETION`/`DUE_DATE`-vs-schedule, Task-series-only; `DUE_DATE` materializes each occurrence onto `due_date` instead of `scheduled_date` while still advancing the cursor on the fixed schedule, see `service::item_series::is_due_date_basis`). The calendar's due-date presets and `list_due`/`prl items due` remain `due_date`-only for now (see the deferred note below).

They follow `due_date`/`has_due_time`'s exact wiring pattern, not a simplified one: each is a split `<input type="date">` + `<input type="time">` pair (not a single `datetime-local` input) plus a companion boolean, because the boolean disambiguates "the user actually typed a time" from "only a date was given and a time got filled in synthetically" — without it the UI can't correctly hide/show the time portion on redisplay. The one deliberate difference from `due_date`: each dedicated screen's own `combine_local_to_utc` (e.g. `src/web_ui/project_tasks/handlers.rs`) takes the synthetic fallback time as a parameter now, because a *window's start* (`scheduled_date`) defaulting to end-of-day would be backwards — `scheduled_date` defaults a bare date to **start**-of-day, while `scheduled_end_date` (like `due_date`) defaults to **end**-of-day, matching how calendar apps treat all-day ranges.

Like `due_date`, both fields are set via a **direct overwrite** in `create_item`/`update_item`/`create_team_item`/`update_team_item` — no service-layer merge/fallback. Every call site that already round-trips `due_date` on update (the web UI's `overlay_*` helpers, `project_calendar.rs`'s full-refetch toggle handlers, `project_templates/`'s child-update handler) does the same for these four fields. `create_item`/`update_item`/`create_team_item`/`update_team_item` reject `scheduled_end_date < scheduled_date` (when both are set) via `ItemError::Invalid`, the same validation-precedent pattern as the item_type-Template rejection above.

**Deferred / partially implemented**: mid-development the user raised whether `scheduled_date`, not `due_date`, should become the *primary* date for tasks (mirroring Todoist's model, where "date" — not a separate deadline — is primary). `item_series`'s own materialization is already `scheduled_date`-primary unconditionally (`src/service/item_series.rs`, `docs/recurring-events-virtual-occurrences-rough-plan.md`), which is the closest thing to this that's landed. **Still out of scope, not yet implemented**: the calendar's preset grouping/sorting, `list_due`/`prl items due`, and any web-UI field-prominence reordering on plain (non-series) items are all still `due_date`-only — a separate future pass, not yet requested.

**Known design tension, deliberately left as-is**: every bare (no-time) date anywhere in this app — `combine_local_to_utc` in the web UI, and the CSV importer's `parse_csv_date` (see the CSV import section below) — is anchored to a real UTC *instant* at the moment it's submitted, computed from the submitter's timezone at that moment (end-of-day for `due_date`/`scheduled_end_date`, start-of-day for `scheduled_date`). That means the stored value is frozen to whichever timezone was in effect at creation/import time, not floating with the viewer: submit a bare due date from London, then view it after flying to New York, and it can display as the previous calendar day (the UTC instant hasn't moved, but which local day it falls in has). Raised by the user during the CSV import work (2026-08-13); a "floating calendar date" model — where a date with `has_due_time == false` redisplays as the same calendar day regardless of viewer timezone, only collapsing to a real instant once an actual time is attached — would be the more intuitive fix, and `has_due_time` is already the right hook for it, but it means changing date *display*, not just parsing, everywhere the app shows a date (web UI, CLI `fmt_date`, MCP responses). Explicitly decided not worth the complexity for now; left as a noted gap, not a bug to silently work around.

### Per-team roles & admin bootstrap (`src/domain/team.rs`, `src/service/teams.rs`)

Team-management authority and item/points authority are two genuinely different things as of Stage C1 of `docs/project-abstraction-plan.md`, both still per-team-or-per-project rather than global (there is no `users.role`/`users.points`). `team_members.role` (`TeamRole`, `Admin`/`Member`, `#[default] Member` — a real enum with `as_str`/`FromStr`/`Display`, not a raw string, following the `ItemType` precedent) gates **team-management** actions only — inviting, renaming, `set_team_member_role` — via `require_team_admin` (`src/service/teams.rs`); a team's creator becomes its first admin automatically (`TeamRepo::create`), and `set_team_member_role` refuses to demote a team's last remaining admin. `team_members` has no `points` column — that was dropped in Stage C4 once nothing read it.

Item/points authority (whether a user can set `points`/`assignedToUserId` on an item — see Points section below) instead reads `project_members.role`, via `require_project_admin`/its non-erroring twin `is_project_admin` (`src/service/projects.rs`) — moved off `team_members.role` in Stage C1 specifically so a personal project (no team at all) can be gated the same way a team-backed one is. `project_members.role` is seeded for a project's owner at creation and kept in sync with an attached team's own membership once one is attached (`attach_team_to_project`). The two authorities can genuinely disagree — a team admin isn't automatically a project admin unless that sync has run.

One narrow bootstrap exception: `caddy_header_middleware` (`src/auth.rs`) promotes a user to admin of exactly one production team's **backing project** (`TODO_BOOTSTRAP_ADMIN_TEAM_ID` still names a *team*, matching caddy-security's own `x-token-user-roles` model — `sync_bootstrap_project_admin` resolves it to that team's project before touching anything) if their `x-token-user-roles` header contains `authp/admin` and that project currently has zero active admins — gated on the project's admin count, not the user's own current role, so the sync fires at most once per project and goes permanently inert afterward (a deliberate in-app demotion is never silently undone). Every other team's/project's roles are managed entirely in-app, via the team detail page's "Manage roles" section, the project members view, `prl teams set-role`/`prl projects set-role`, or the `set_team_member_role`/`set_project_member_role` MCP tools/JSON API operations — none of which touch caddy-security.

### Points & the activity log (`src/service/team_items.rs`, `src/service/activity_log.rs`, `src/storage/sqlite/activity_log.rs`)

Points exist **only on team-backed-project items**, never personal-project ones — `points: Option<i32>` on `Item`, top-level-only (rejected alongside `parentItemId`, the same shape as the item_type check above), and settable only by that project's admin (`create_team_item`/`update_team_item` — still the functions that actually implement this, see the dispatch note in Recurrence above — silently strip/preserve a non-admin's attempted value rather than rejecting the rest of the request; "that project's admin" means `project_members.role`, checked via `is_project_admin`, not `team_members.role` — see Per-team roles above). Completing a points-bearing top-level team item awards its `points` to `assigned_to_user_id` (never whoever clicked complete) via `ProjectRepo::add_project_points` — writing to `project_members.points`; `team_members.points` no longer exists at all, dropped in Stage C4 of `docs/project-abstraction-plan.md`. **Team item completion is no longer assignment-gated** (resolved 2026-08-22, see `docs/archived/archived_issues_and_features.md`'s "Allow anyone to complete tasks not assigned to them"/"Remove restriction that unassigned items cannot be completed" entries): any project member may complete any team item, whether it's assigned to them, to someone else, or to no one — `update_team_item` (`src/service/team_items.rs`) no longer rejects on `assigned_to_user_id() != requester_user_id` or `None`. Points still only ever go to `assigned_to_user_id`, never the completer, so an unassigned item's completion simply has no one to log/award against and produces no activity-log entry at all.

**Logging is broader than points-awarding, as of the "unify completion-undo" pass (2026-08-19, `docs/archived/archived_issues_and_features.md`).** Every top-level completion — team or personal, points-bearing or not — logs an `activity_log` row; only awarding points is still points-gated. `team_items::update_team_item`'s completion branch always calls `log_activity` (`points_delta: item.points().unwrap_or(0)`), calling `add_project_points` only when that's nonzero. `items::update_item` (the personal path, previously with zero `activity_log` involvement) gained the identical shape: `log_activity(team_id: None, project_id: Some(item.project_id), ..., points_delta: 0)` on a top-level completion, and the matching `most_recent_unreversed`+`reverse_entry` lookup on uncomplete. Un-completing a non-recurring item — team or personal, via either the checkbox or the activity feed's manual undo (see below) — reverses the award (or the points-less log entry) by looking up the most recent unreversed log entry for that item+user.

`ItemSeries` (see Recurrence above) carries its own `assigned_to_user_id`/`points` fields, mirroring an item's `TeamAssignment` one level up — settable only on a `Task`-typed series on a team-backed project (`service::item_series::resolve_series_assignment`; an `Event`-typed series or a personal-project series rejects both outright, `points` further gated on the requester being that project's admin, silently dropped otherwise, same convention as `create_team_item`). `get_or_materialize_occurrence` (`src/service/item_series.rs`) carries both fields onto every occurrence it materializes via `CreateProjectItemParams`, so a materialized occurrence's completion awards points exactly like any other team item — there is no series-level points bookkeeping separate from the per-occurrence item mechanism described above.

The activity feed's manual "Undo" (`PUT /teams/{teamId}/activity-log/{entryId}/undo`, `prl teams undo-activity`, or the web UI's project activity feed at `/web/projects/:project_id/activity`) is a **separate action on the activity-log entry itself**, not the item — it predates item-level recurrence's Stage 10 retirement (see Recurrence above), when a recurring item's completion deleted the old row (so it had nothing left to un-complete in place). That specific "item is gone" case no longer exists for anything (a materialized series occurrence is never deleted), so as of the "unify completion-undo" pass (2026-08-19, `docs/archived/archived_issues_and_features.md`), manual undo now **also reopens the item** when one still exists and is still complete: `service::activity_log::reverse_and_reopen` — the shared core both `undo_activity_log_entry` (team-scoped, legacy) and `undo_project_activity_log_entry` (project-scoped, what the web UI actually calls) delegate to — pre-checks `item_series::validate_uncompletable` (the same "only the series' current cursor occurrence" rule the checkbox path enforces — see Recurrence above), *then* reverses the entry's points via `reverse_entry`, then delegates into `project_items::update_project_item`'s own `complete: false` path (`reopen_item_if_still_complete`) for the actual reopen — the exact same path the checkbox itself uses, so `item_series`'s cursor restore (`record_task_uncompletion`) and every completion-guard rule below apply identically regardless of which UI triggered the uncomplete: there is exactly one "uncomplete an item" implementation, not two that could drift. The pre-check specifically has to run *before* `reverse_entry`, not just rely on the reopen step's own internal validation — same-day fix, since `reverse_entry` has no undo of its own: rejecting only at the reopen step would have left points clawed back and the entry marked reversed for an out-of-order series occurrence that still failed to reopen, with no way to restore either.

Both the automatic (checkbox) and manual (entry-targeted) *points* reversal still share one `reverse_entry` function (`src/service/activity_log.rs`) and coordinate through a `reversed` flag on the log row — `mark_reversed`'s `WHERE reversed = 0` guard is the only atomic "claim" either path has, so whichever gets there first wins and the other silently no-ops (and the reopen step is itself a no-op once the item's already incomplete, so no double-uncomplete either). `activity_log` rows carry a nullable `team_id` (relaxed from `NOT NULL` by the `ActivityLogTeamIdNullable` migration in the same pass — `None` for a personal item's log row, which has no team at all) and a nullable `project_id` — `team_id` predates the Project abstraction and stayed live through Stage C4 and beyond, because the legacy `ListTeamActivityLog`/`UndoActivityLogEntry` Smithy operations were never retired (unlike `Item`/`TeamItem` — see Smithy section above) and still read it; `prl teams activity`/`undo-activity` and the MCP `list_team_activity_log`/`undo_activity_log_entry` tools still call them by `team_id`, unchanged by this pass (no Smithy/codegen touch — the web UI's activity feed already called the service layer directly, so it only needed the new project-scoped function, not a new operation). `project_id` is the column every other read (including the reopen logic above) keys off instead. `activity_log` is scoped to completion events only (not general item CRUD history), and append-only with no retention policy — reversal only flips a flag, never deletes a row.

### Priority (`src/domain/item.rs`, `src/domain/item_series.rs`, `src/service/items.rs`, `src/service/team_items.rs`, `src/service/item_series.rs`)

`priority: Option<i32>` (1 = highest, 4 = lowest, `None` = unset/lowest) exists on `Task`-typed items and `Task`-typed item series, and drives sort order: `storage::sqlite::items`'s `ORDER BY COALESCE(priority, 5) ASC, COALESCE(due_date, ...) ASC` for every plain item list (`list`, `list_children`, `list_by_project`, etc. — `list_due*`/`list_templates*` are the deliberate exceptions, staying `due_date`-only for now, same "not yet requested" carve-out as the Scheduled start/end section's deferred note), and the equivalent `(priority_rank, due_date_timestamp)` Rust-side tuple sort in `web_ui::project_tasks::sort_key`/`web_ui::all_projects_tasks` (the two screens that merge real items with not-yet-materialized series occurrences and so can't rely on SQL order alone). `priority_rank` maps `None` to `5` so it always sorts after `4`, matching "4 takes precedence over no priority set."

Deliberately **not** modeled like `points`/`assigned_to_user_id` despite the structural resemblance (a `Task`-only field living inside `ItemType::Task`/`ItemSeries`): it's a plain personal-productivity field, so it carries none of `TeamAssignment`'s restrictions — settable on a personal *or* team-backed project, on a child item as well as top-level, by any project member, never admin-gated. `Item::priority` therefore lives as its own field directly on the `ItemType::Task` variant (sibling to `source_event_id`), not nested inside `TeamAssignment` or the cross-kind-shared `Recurrence`/`Schedule` structs. `ItemSeries::priority` is a flat field mirroring `points`, but `service::item_series::validate_series_priority` — unlike `resolve_series_assignment` — only checks `item_type == Task` and the 1–4 range, never a team-backed-project or admin requirement. `get_or_materialize_occurrence` carries `series.priority` onto every occurrence it materializes, the same way it already does `points`/`assigned_to_user_id`; a still-virtual/skipped occurrence also carries the series' `priority` via `service::item_series::ProjectOccurrence`, so the merged sort above ranks an unmaterialized occurrence correctly too.

`Item::validate()` rejects a value outside 1–4. `priority` follows `event_type`'s direct-overwrite convention on update (no fallback to `current`) — every `UpdateItemParams`/`UpdateTeamItemParams`/`UpdateProjectItemParams` construction site that isn't intentionally clearing it must round-trip `current.priority()` explicitly (the web UI's `overlay_*`-based forms already do, via `overlay_i32`; `prl items done` round-trips it the same way it already does `points`/`dueOffsetDays`). It's also part of `is_pure_complete_toggle`'s explicit field allowlist (`src/service/items.rs`) — a completed item's priority can't be changed without un-completing it first, same as every other field there. `copy_template_children`/`copy_template_children_to_event` carry a template child's own `priority` onto each copy, the same as `due_offset_days`.

### Completion-transition guards (`src/service/items.rs`, `src/service/team_items.rs`)

Two rules apply to **both personal and team items**, independent of points: (1) completing an item is rejected while it has any incomplete *direct* child (`has_incomplete_children`) — direct-children-only is sufficient by induction, since each child was itself gated the same way when it was completed; (2) once `complete == true`, editing any field but `complete` is rejected (`is_pure_complete_toggle`, an explicit field allowlist, not a derived `PartialEq`, since a freshly-built `Item` spuriously differs from `current` on defaulted fields like the query-computed `has_children`) — the only way to edit a completed item again is to un-complete it first. The web UI hides each read-only detail view's "Edit" link when `complete == true`; template children are exempt (no `complete` concept).

### CSV import & the import template (`src/service/import.rs`, `model/src/main/smithy/item_import.smithy`)

`ImportProjectItems` (`POST /projects/{projectId}/items/import`) and `GetItemImportTemplate` (`GET /items/import-template`) are deliberately **CLI/MCP-only — no web UI screen**. `GetItemImportTemplate` is the one operation outside `/users`/`/teams`/`/projects` — it needed its own new `/items` route registration in `src/main.rs`'s `api_router`, in both auth-mode branches.

The server, not the caller, parses the raw CSV (`csv: String` on the input) — this centralizes 100% of parsing + validation + creation logic in `src/service/import.rs::import_project_items`, which reuses `project_items::create_project_item`'s existing dispatch/validation with zero duplication (the same `TEMPLATE`-rejection/scheduled-date rules described above all apply per-row for free; `recurrence` is checked directly by `import_project_items` itself, not inherited from `create_project_item` — see the `recurrence`/`recurrenceBasis` note below). `prl`/the MCP server just read/pass a file's raw text through unchanged — neither needed a `csv` parsing dependency of their own.

**Best-effort, not transactional**: every row is attempted independently via its own `create_project_item` call; valid rows are created, invalid ones collect into a per-row `ImportItemResult { rowNumber, success, itemId, error }` rather than aborting the whole import. `rowNumber` counts the header as row 1, so the first data row is 2. Column mapping is header-driven (order-independent) — extra or missing optional columns are simply never looked up rather than erroring. `parentItemId` may be given per row but must reference an item that already exists, not another row in the same file — there's no intra-file parent/child resolution in this version.

`format` (on both the request and the CSV-parsing dispatch inside `import_project_items`) is a plain, unenforced `String` defaulting to `"PRL"` — following the `eventType` precedent above, not the `ItemType` exception — with a single `match format { "PRL" => ..., other => reject }` as the seam for a future format. `PRL` is this app's native, lossless format: column headers match the API's own JSON field names exactly (`name, description, dueDate, scheduledDate, scheduledEndDate, complete, hasDueTime, hasScheduledTime, hasEndTime, itemType, eventType, dueOffsetDays, parentItemId, assignedToUserId, points, priority, sourceEventId`), dates use the same `YYYY-MM-DD`-or-Unix-timestamp convention `--due`/`--scheduled` already do. There is no `recurrence`/`recurrenceBasis` column (Stage 10 gap 4 of `docs/recurring-events-virtual-occurrences-rough-plan.md`, 2026-08-15): a row with a `recurrence` column set is a hard error for that row (`ImportItemResult { success: false, ... }`, same as any other invalid row), not a silent drop — bulk-import is for loading a batch of items, not authoring a recurring series; create a series once via the UI/CLI/MCP series endpoints instead. A `"TODOIST"` format was explored for feasibility but is **not implemented**: Todoist's own CSV export (`TYPE,CONTENT,DESCRIPTION,IS_COLLAPSED,PRIORITY,INDENT,AUTHOR,RESPONSIBLE,DATE,DATE_LANG,TIMEZONE,DURATION,DURATION_UNIT,DEADLINE,DEADLINE_LANG`) would need: skipping non-`task` `TYPE` rows, a natural-language date parser for its `DATE` column (`"in 15 days"`, `"yesterday"` — this app has no such parser), flattening its `INDENT`-based nesting (conflicts with the flat-only-v1 rule above), and has no machine-readable "complete" column at all; `PRIORITY`/`AUTHOR`/`RESPONSIBLE`/`DURATION`/`DURATION_UNIT` have no equivalent in this model and would be dropped. `DEADLINE` (a clean ISO date) is the one column that maps well, to `dueDate`.

A bare (no-time) `dueDate`/`scheduledDate`/`scheduledEndDate` in the CSV is interpreted in the *caller's* local time via a `timezoneOffsetMinutes` request field (`parse_csv_date` in `src/service/import.rs`, mirroring the web UI's `combine_local_to_utc` — same end-of-day/start-of-day-per-field convention as Scheduled start/end above) rather than literal UTC — `prl` computes this automatically from the local machine's timezone (`todo-cli/src/items.rs`'s `Import` handler), and the MCP server defaults it to its own host's local offset if the caller doesn't supply one (`mcp-server/src/index.ts`). Fixed 2026-08-13 after a real bug report: without it, a bare date near a timezone's midnight boundary landed on the wrong calendar day once viewed back in local time. This still anchors to an *instant* computed from whoever's timezone was in effect at import time, not a floating calendar date — see the "Known design tension" note in Scheduled start/end above, which applies here identically (raised by the same conversation, deliberately left as-is).

`GetItemImportTemplate` returns a static 3-row constant (`ITEM_IMPORT_TEMPLATE_CSV` in `src/service/import.rs`) — one Task, one Event, one Simple item, deliberately no `TEMPLATE` row, since `itemType: TEMPLATE` is rejected on this path the same way it's rejected on `create_item`/`create_team_item` (see Events section above — templates have their own creation flow).

CLI: `prl items import <file> --project <id> [--format PRL]` reads the file locally and posts its text; `prl items template [--output <path>]` prints to stdout by default (`todo-cli/src/items.rs`). MCP tools: `import_project_items`/`get_item_import_template` (`mcp-server/src/index.ts`).

### Web UI (`src/web_ui/` + `templates/`)

Server-rendered Askama + htmx UI — there is no browser-side SPA or generated TS client involved. `templates/base.html` is the one root document (`{% extends "base.html" %}` everywhere else); `hx-boost="true" hx-target="#page" hx-select="#page" hx-swap="innerHTML"` on `<body>` keeps the header/scripts stable across boosted navigation while `#page` content swaps. Individual mutations that shouldn't touch the rest of the page (row toggle/delete, a detail form's own save) scope their own narrower `hx-target`/`hx-select` instead of inheriting the body-level one.

The desktop sidebar (`templates/nav.html`'s `#sidebar-desktop`, `lg:`-only) is collapsible via a chevron button in the header, independent of the mobile hamburger's off-canvas sidebar. `<main id="page">` never reserves space for it and never changes on toggle — `#sidebar-desktop` is a fixed-position overlay (`z-30`, above `#page`'s implicit `z-auto`) that slides via `transform: translateX(-100%)` (`html.sidebar-collapsed`, `styles/input.css`), a compositor-only property that triggers no layout recalculation, so toggling can never reflow `#page`'s own box even mid-transition — confirmed via a live Playwright check asserting `#page`'s `getBoundingClientRect()` is byte-identical before/during/after toggling. The deliberate tradeoff: on narrower desktop widths the expanded sidebar can overlap `#page`'s centered content rather than pushing it aside — chosen over any layout shift. State is `localStorage`-only (`toggleSidebar()` in `base.html`), read synchronously in `<head>` before `<body>` renders so a fresh/non-boosted load (sidebar links use `hx-boost="false"`, see above table — every navigation between sections is a full load) never flashes one state before the other. Collapsing also sets the sidebar `visibility: hidden` — without it, its links would still sit in tab order and remain keyboard-focusable despite `transform` having moved them off-screen.

A `src/service/` layer (`items.rs`, `team_items.rs`, `project_items.rs`, `projects.rs`, `teams.rs`, `templates.rs`, `activity_log.rs`, plus a shared `ItemError` in `error.rs`) holds business logic used by both `src/json_api/` and `src/web_ui/`, so the two presentation layers stay thin wrappers rather than duplicating logic. `ItemError` itself is presentation-agnostic (no HTTP/HTML knowledge); `src/web_ui/error.rs` adds `impl IntoResponse for ItemError` (HTML error fragment + status code) — that split must be preserved for any error-handling changes.

The **row-editing convention**, established by the now-retired generic Items/Team-Items catch-alls and followed identically by every dedicated screen (`project_tasks/`, `project_events/`, `project_simple_lists/`, and template children in `project_templates/` — all under `src/web_ui/`, not to be confused with the top-level `templates/` Askama directory or `src/service/templates.rs`): no inline click-to-edit, and — since the read-only-detail pass below — no edit-form-on-click either. A row's name is a boosted link to that item's own **read-only** detail page (e.g. `GET /projects/:project_id/tasks/:id`, a `DetailView`-rendered fragment in a uniquely-`id`'d wrapper, e.g. `#item-{id}-view`), which has its own "Edit" link to a sibling `GET .../:id/edit`-style route holding the actual edit `<form>` (unchanged: still inside `#item-{id}-fields`, still PUTing back to the non-`/edit` resource URL with `hx-target`/`hx-select` scoped to that same wrapper id — this split only changed what a plain `GET` renders, not the save flow, which still stays on `/edit` and shows the in-place `just_saved` toast). The read-only view also carries a complete-toggle checkbox identical to the row's own, so marking an item done doesn't require opening Edit — because that checkbox PUTs to the same endpoint the row-checkbox and the edit form already PUT to, each screen's own `update_*_form` handler renders **three** fragments concatenated into one response body (row + fields + view), each caller's own `hx-select` plucking out only its own id. Template children are the one variant without the toggle: their edit form has no `complete` concept at all (hardcoded `false` in `update_project_template_child_form`), so their read-only view has nothing to PUT against and that handler's response stays the original two-fragment (row + fields) shape. Templates themselves (as opposed to their children) never had an edit form and are untouched by any of this; `teams.rs`'s own detail page is untouched too — despite structurally mirroring the same page-per-resource layout, it's a member-management page (invite/accept/leave), not a fields-editing one, so it was never actually part of this convention's form-on-click half.

**Screens are project-scoped, not personal/team-scoped** — the original per-item-type-times-personal/team screen split (`tasks.rs`+`team_tasks.rs`, `events.rs`+`team_events.rs`, `simple_lists.rs`+`team_simple_lists.rs`, `templates.rs`+`team_templates.rs`, `dashboard.rs`) was collapsed once every screen was rebuilt on top of `ProjectItem` (Stage B5 of `docs/project-abstraction-plan.md`): a personal item just lives on a project with no backing team, so one screen per item type now serves both cases, dispatching on `project.team_id` internally (e.g. for whether to show an "Assign to" dropdown or points field — gated by `is_project_admin`, see Per-team roles above) rather than living at a different URL. `src/web_ui/nav.rs`'s `ActiveContext` is `Project(String) | AllProjects | None` (no persisted "active project" — always derived from the URL), replacing the old Personal/Team switcher; `SidebarSection` (`Tasks`/`Events`/`SimpleLists`/`Templates`/`None`) still drives the sidebar the same way for a `Project(id)` page, just resolved against the page's active project via `section_href` instead of a personal/team split. `ActiveContext::AllProjects` (added in `docs/all-projects-landing-plan.md`, see below) is the cross-project counterpart: `build_nav_html`'s matching arm builds `section_links` from a fixed `[Tasks → /web/tasks, Events → /web/events]` list rather than `section_href` (which is project-scoped), sets `calendar_href = Some("/web/calendar")`, and `activity_href = None`.

Screens, all under `src/web_ui/` mounted at `/projects/:project_id/...` unless noted: `project_tasks/` (`/tasks`, hardcoding `itemType: TASK` on create/update), `project_events/` (`/events`, hardcoding `itemType: EVENT`/`parentItemId: None`, scheduled-window-primary display, its own `/events/:id/children` sub-item routes), `project_simple_lists/` (`/simple-lists`, hardcoding `itemType: SIMPLE`, no date/scheduling/recurrence fields anywhere since `Item::validate` rejects all of those for `ItemType::Simple`), `project_templates/` (`/templates`, template CRUD + a "Use" flow that recursively copies a template's child subtree onto a newly created real item via `copy_template_children` in `service::items`; a template's own `eventType` field, set at creation, is what the auto-trigger mechanism in the Events section above matches against). Each of `project_tasks/`, `project_events/`, `project_simple_lists/` has a "Save as template" button (e.g. `save_project_task_as_template`) posting into `project_templates/`.

Outside the per-type screens: `all_projects_tasks.rs` (`/web/tasks`, the **default landing page** — `GET /` and the header logo link redirect here, see Server section above — an all-projects Tasks list mirroring `project_tasks/`'s per-project list shape: top-level Task items + expandable children, no flattening-by-date across item types, no "+ New Task" button since creation is inherently project-scoped) and `all_projects_events.rs` (`/web/events`, the same shape for Events — no completion/assignment/points, since Events aren't completable) are the cross-project counterparts to `project_tasks/`/`project_events/`, added by `docs/all-projects-landing-plan.md` (see below) and registered under `ActiveContext::AllProjects`. `main_calendar.rs` (`/web/calendar`, the calendar grid + day-drawer — no longer the default landing page as of that same plan, and no longer the sole cross-project screen; its flat list view, formerly at `/web/calendar/list`, was removed entirely, not merged into the two screens above) is registered under `ActiveContext::AllProjects` too. Stage 8 of `docs/calendar-day-drawer-plan.md` renamed this module and its routes from `main_dashboard.rs`/`/web/dashboard` — the old `/web/dashboard` and `/web/dashboard/calendar` paths are kept only as redirects to `/web/calendar`, and `/web/dashboard/list` redirects to `/web/tasks`, cheap insurance against a stale link/bookmark; the `.../calendar/day` day-drawer fragment route and the `.../calendar/projects/:project_id/items/:item_id` toggle route have no legacy counterpart since neither is ever bookmarked or linked to directly), `projects.rs` (`/web/projects`, the project picker/list page), `project_calendar.rs` (`/projects/:project_id/calendar`, due-item rows for that one project — scoped from the start via `ItemRepo::list_due_by_project`, so unlike the old cross-team `dashboard.rs` it has nothing to merge; same grid-is-default/legacy-`/dashboard`-redirects shape as `main_calendar.rs`, renamed from `project_dashboard.rs`/`/projects/:project_id/dashboard` in the same Stage 8 pass — its own flat list view, formerly at `.../calendar/list`, was removed in the same pass as `main_calendar.rs`'s, and its `/dashboard/list` redirect now points at `/web/projects/{project_id}/tasks`), `project_activity.rs` (`/projects/:project_id/activity[/:entry_id/undo]`, the points activity feed and manual-undo UI for a team-backed project — reads `activity_log.project_id`, not `team_id`, see Points section above), `assigned_items.rs` (`/web/assigned-items`, read-only cross-project "assigned to me" list — mirroring `prl items assigned`/`list_assigned_items`'s own cross-project reach), `teams.rs` (`/web/teams`, team CRUD/membership — teams remain a separate concept from projects, attachable/detachable via `attach_team_to_project`/`detach_team_from_project`), `nav.rs` (not a screen itself — builds the shared sidebar/project-switcher `nav_html` fragment every page-level template embeds), and `login.rs` (`GET /web/login`, the one route exempt from the `/web/*` auth middleware — see Auth section above).

`main_calendar.rs` (added 2026-08-20 as `main_dashboard.rs`, renamed in Stage 8 above) is additive to the per-project calendars, not a replacement — same read-only-fan-out shape as `assigned_items.rs`, just richer: it loops over every project `ProjectRepo::list_for_user` returns and reuses `project_calendar.rs`'s own per-project merge logic (real due items + the Stage A unified series-occurrence query) per project rather than a single cross-project SQL query, tagging each row/calendar entry with its project's name. It applies a filter the per-project calendar has no equivalent of: Events always show regardless of project/assignment, Tasks show unrestricted on a personal project but only when assigned to the requester on a team-backed one (otherwise every teammate's tasks would show, defeating the screen's "what's mine, across everything" purpose). `all_projects_tasks.rs`/`all_projects_events.rs` apply the same filter shape (a Task-only `task_included` predicate mirroring `is_included`'s Task arm; Events are unrestricted, per `is_included`'s own `Event => true` arm) but duplicate it locally rather than sharing code with `main_calendar.rs`, per this codebase's established "duplicate small per-screen helpers" precedent (see `project_tasks`/`project_events` themselves). The sidebar's "Home" link (bottom fixed-links section) now points at `/web/tasks`.

The original generic personal (`/web/items`) and team-scoped (`/web/team-items/:team_id`) catch-all screens were retired once every item type had a fully dedicated screen in both contexts; those per-type personal/team screens were themselves later collapsed into the single project-scoped set described above. `GET /` and `templates/nav.html`'s logo link landed on `/web/projects` (the project picker) from that collapse until 2026-08-20, when both moved to `/web/dashboard` (the new cross-project dashboard above, renamed to `/web/calendar` in Stage 8 of `docs/calendar-day-drawer-plan.md`), and then to `/web/tasks` (the all-projects Tasks list above) per `docs/all-projects-landing-plan.md`. `nav.rs::section_href`'s `SidebarSection::None` fallback (used by pages with no single natural section, once a project *is* active) lands on that project's own Calendar, unaffected by this change.

The tz offset (`new Date().getTimezoneOffset()`) is sent as an `X-Tz-Offset-Minutes` **header** (via a `htmx:configRequest` listener in `base.html`), not a form/query parameter — a parameter there previously leaked into `hx-push-url`'d URLs and broke `hx-select="#page"` navigation. A `tz_offset` cookie (set on every page load) is the fallback for non-htmx requests (bookmarks, hard refresh). See `TzOffset` in `src/web_ui/mod.rs`.

## Key Workflows

**Adding/changing a Smithy operation:**

1. Edit `.smithy` file
2. `task codegen`
3. Fix Rust compile errors (the generated types changed)
4. Add/update handler in `src/main.rs` and wire into `PeoplesRepublicOfLists::builder(...)`

See the touch-point checklist below for all files that may need updating.

**Adding a DB column:**

1. Add the column to `CREATE TABLE IF NOT EXISTS` in `create_pool()` (sqlite.rs) — this is what makes a fresh DB correct without ever running the migration below
2. Add a new file under `src/storage/migrations/` implementing `Migration` with the next version number; guard each `ALTER TABLE ... ADD COLUMN` with `if !column_exists(conn, "items", "...").await? { ... }` (SQLite has no `ADD COLUMN IF NOT EXISTS`), and register it in `all_migrations()`
3. Update relevant SELECT/INSERT/UPDATE queries and row mapping

**Web UI-only change (no Smithy or handler-logic changes):**

- Edit `templates/*.html` → `cargo build` (Askama embeds templates at compile time, so a Rust rebuild is required even for template-only edits — there's no separate template-build step)
- If Tailwind classes changed: also run `task web-styles`

**Switching auth modes:**

- Set `TODO_AUTH_MODE=caddy` to trust caddy-security headers (no Google/JWT env vars needed)
- Set `TODO_AUTH_MODE=internal` (or unset) to use the built-in OAuth flow
- For local dev in caddy mode without Caddy: set `TODO_DEV_EMAIL=you@example.com`

## Touch-Point Checklist

Every place that must be updated when the Smithy model changes. The generated crates (`todo-server-sdk/`, `todo-client/`, `todo-typescript-client/`) update themselves via `task codegen` — everything else is hand-written and must be updated manually.

### Adding or removing an operation

| File | What to do |
|------|-----------|
| `model/src/main/smithy/*.smithy` | Add/remove the operation definition |
| *(run `task codegen`)* | Regenerates Rust SDKs + TS client source |
| `src/main.rs` | Add/remove the handler function; wire/unwire from `PeoplesRepublicOfLists::builder(...)` |
| `src/json_api/mod.rs` / `src/web_ui/mod.rs` | If creating a new handler file, add `pub mod <module>;` here (whichever layer it belongs to) |
| `src/service/*.rs` | Add/remove the shared business-logic function, if applicable — see Web UI section above |
| `src/web_ui/**/*.rs` + `templates/**/*.html` | Add/remove the web UI screen/route for it, and wire the route in `build_web_router()` in `src/main.rs` |
| `mcp-server/src/index.ts` | Add/remove tool definition in the tools list; add/remove `case` in the switch |
| *(run `cd mcp-server && npm run build`)* | Recompile the MCP server source → `dist/index.js`; changes are not live until this runs |
| `todo-cli/src/main.rs` | Add/remove subcommand variant and match arm in the relevant `cmd_*` function |
| `docs/prl-user-guide.md` | Document the new command or remove it |

### Renaming the service

| File | What to change |
|------|---------------|
| `model/src/main/smithy/service.smithy` | `service OldName {` → `service NewName {` |
| `model/smithy-build.json` | All `"service": "common#OldName"` → `"service": "common#NewName"` |
| *(run `task codegen`)* | |
| `src/main.rs` | `OldName`, `OldNameConfig` imports and usage |

### Renaming an error type

| File | What to change |
|------|---------------|
| `model/src/main/smithy/errors.smithy` | Rename the `structure` |
| All other `.smithy` files | Update references in `errors: [...]` lists |
| `model/smithy-build.json` | No change needed (errors aren't referenced here) |
| *(run `task codegen`)* | |
| `src/main.rs` | `error::OldErrorName` usage in handler return types and `internal()`/`not_found()` helpers |

### Docker builds

`todo-server-sdk/` is gitignored (generated). The Dockerfile copies it from the local filesystem, so **`task codegen` must be run before `task docker-build`**. `task docker-build` and `task docker-release` do this automatically. (`todo-typescript-client/` is also generated by codegen but no longer copied into the Docker build — nothing consumes it since `frontend/` was removed.)
